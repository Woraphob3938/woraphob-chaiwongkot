# FitConnect: การชำระเงิน แชต รีวิว และตรวจข้อมูล

วันที่: 1 สิงหาคม 2026

สถานะ: ข้อตกลงการออกแบบได้รับการยืนยันแล้ว และรอตรวจทานสเปกฉบับเขียน

ขอบเขต: ขั้นตอนที่ 7 ถึง 10 ของระบบ FitConnect

## 1. เป้าหมาย

ทำให้เส้นทางการจองหลังเทรนเนอร์ตอบรับใช้งานกับข้อมูลจริงได้ครบวงจร:

1. เทรนเนอร์ระบุราคาสุดท้ายตอนตอบรับคำขอจอง
2. สมาชิกอัปโหลดหลักฐานการโอนและยอดที่ชำระ
3. แอดมินตรวจหลักฐานแล้วอนุมัติหรือส่งกลับให้แก้ไข
4. สมาชิกและเทรนเนอร์สนทนาในห้องที่ผูกกับการจอง
5. เทรนเนอร์ปิดงานหลังเลยเวลานัด
6. สมาชิกให้คะแนนและเขียนรีวิวได้หนึ่งครั้ง
7. ทุกขั้นตอนมีข้อมูลอ้างอิงที่ตรวจสอบต่อใน phpMyAdmin ได้

ระบบยังใช้ Next.js, PHP API ภายใต้ XAMPP และ MySQL ตามสถาปัตยกรรมปัจจุบัน ข้อความบนหน้าเว็บต้องบอกตามจริงว่าหลักฐานการโอนผ่านการตรวจโดยแอดมิน ไม่ใช่การยืนยันยอดจากธนาคารอัตโนมัติ

## 2. สิ่งที่อยู่นอกขอบเขต

- ระบบตัดบัตร เครดิต กระเป๋าเงินดิจิทัล หรือเชื่อมต่อธนาคาร
- การคืนเงินอัตโนมัติ
- การแจ้งเตือนผ่านอีเมล LINE หรือ push notification
- แชตแบบ WebSocket หรือบริการแชตภายนอก
- การโทรด้วยเสียงหรือวิดีโอ
- การแก้ไขหรือลบรีวิวหลังเผยแพร่
- การเปิดเผยไฟล์สลิปหรือไฟล์แนบผ่าน URL สาธารณะ
- ระบบร้องเรียนและการไกล่เกลี่ยหลังจบงาน

## 3. แนวทางที่เลือก

ต่อยอด PHP API และ MySQL ที่มีอยู่ โดยให้หน้าแชตดึงข้อความใหม่ทุกประมาณ 5 วินาที วิธีนี้ทำงานกับ XAMPP ได้ทันที ดูแลโค้ดได้จากโครงการเดียว และย้ายไป PHP/MySQL hosting ในอนาคตได้โดยไม่ต้องพึ่งบริการแชตแยกต่างหาก

ตารางที่มีอยู่รองรับงานหลักแล้ว ได้แก่ `bookings`, `booking_status_history`, `payments`, `chat_rooms`, `messages` และ `reviews` จึงใช้ schema เดิมก่อน หากการตรวจระหว่างพัฒนาพบว่าคอลัมน์หรือดัชนีใดขาดจริง จึงเพิ่ม migration เฉพาะส่วนนั้นพร้อมอธิบายเหตุผลในแผนพัฒนา

## 4. หลักการออกแบบหน้าจอ

หน้าจอใหม่ใช้ระบบภาพ Athlete Credential Workbench ใน `DESIGN.md` ต่อเนื่องจากขั้นตอนค้นหาและจอง:

- ใช้ ledger, queue, เส้นแบ่ง และพื้นที่ทำงานแทนการเรียงการ์ดตกแต่ง
- ใช้สีเขียวมะนาวกับการกระทำหลักและรายการที่กำลังเลือกเท่านั้น
- แสดงราคา เวลา รหัส และสถานะด้วยรูปแบบที่อ่านได้เร็ว
- มี CTA หลักหนึ่งรายการต่อบริบท
- สถานะต้องมีข้อความกำกับ ไม่ใช้สีอย่างเดียว
- รักษาโทน utilitarian athletic ที่แข็งแรง ตรงไปตรงมา และใช้งานจริง

กลุ่มผู้ใช้คือสมาชิก เทรนเนอร์ และแอดมิน เป้าหมายของหน้าจอคือทำให้แต่ละคนเห็นข้อเท็จจริงชุดเดียวกันและรู้ว่าต้องทำอะไรต่อ

## 5. สถานะและลำดับงาน

### 5.1 เส้นทางหลัก

```text
pending_trainer
  -> เทรนเนอร์ตอบรับพร้อมราคาสุดท้าย
awaiting_payment
  -> สมาชิกส่งยอดโอนและสลิป
payment_review
  -> แอดมินอนุมัติ
confirmed
  -> เลยเวลานัดและเทรนเนอร์กดจบงาน
completed
  -> สมาชิกส่งรีวิวหนึ่งครั้ง
review published
```

### 5.2 สลิปไม่ผ่าน

```text
payment_review
  -> แอดมินไม่อนุมัติพร้อมเหตุผล
awaiting_payment
  -> สมาชิกส่งสลิปใหม่
payment_review
```

รายการชำระเงินที่ไม่ผ่านยังอยู่ใน `payments` พร้อมสถานะและเหตุผลเดิม การส่งใหม่สร้าง payment แถวใหม่ เพื่อให้ตรวจย้อนหลังได้ว่าเกิดอะไรขึ้นบ้าง

### 5.3 การยกเลิก

การจองที่เข้าสู่ `cancelled` ยังคงเก็บข้อความเดิมไว้ ห้องแชตเปิดอ่านได้ แต่ช่องส่งข้อความถูกปิดและอธิบายว่าไม่สามารถส่งข้อความเพิ่มได้

## 7. API contract

ทุก endpoint ใช้ response envelope และรูปแบบ error เดิมของโครงการ กฎสำคัญต้องตรวจใน PHP API แม้หน้าเว็บจะตรวจเบื้องต้นแล้ว

### 7.1 เทรนเนอร์ตอบรับพร้อมราคาสุดท้าย

ใช้ endpoint เดิม:

`PATCH /v1/bookings/{publicId}/status`

request body:

```json
{
  "status": "awaiting_payment",
  "quotedPrice": 1200
}
```

กฎ:

- ผู้เรียกต้องเป็นเทรนเนอร์เจ้าของ booking
- booking ต้องมีสถานะ `pending_trainer`
- `quotedPrice` ต้องเป็นตัวเลขมากกว่า 0 และมีทศนิยมไม่เกิน 2 ตำแหน่ง
- ราคาเก็บใน `bookings.quoted_price`
- booking เปลี่ยนเป็น `awaiting_payment`
- เพิ่ม `booking_status_history`
- การเปลี่ยน booking, ราคา และประวัติทำใน transaction เดียวกัน
- หากคำขอถูกตอบไปแล้ว ให้ตอบ `409` โดยไม่เขียนทับราคาเดิม

### 7.2 รายการจองตามบทบาท

ปรับ `GET /v1/bookings` ให้ส่งข้อมูลที่หน้าจอต้องใช้ตามสิทธิ์:

- `publicId`, `status`, `paymentStatus`
- ชื่อสมาชิกและเทรนเนอร์ตามบทบาทที่กำลังดู
- เวลาเริ่ม เวลาสิ้นสุด สถานที่ และประเภทบริการ
- `quotedPrice`
- `chatRoomId`
- payment ล่าสุดพร้อมยอด สถานะ เหตุผล และเวลาส่ง
- ข้อมูลรีวิวของ booking เมื่อมีแล้ว
- flags ที่คำนวณจากกฎฝั่ง server เช่น `canPay`, `canChat`, `canComplete`, `canReview`

หน้าเว็บใช้ flags เพื่อแสดงปุ่ม แต่ API ยังตรวจสิทธิ์และสถานะซ้ำตอนเปลี่ยนข้อมูล

### 7.3 สมาชิกส่งหลักฐานการโอน

ใช้ `POST /v1/payments` แบบ `multipart/form-data`

fields:

- `bookingId`: public id ของการจอง
- `amount`: ยอดที่สมาชิกระบุว่าโอนแล้ว
- `slip`: ไฟล์ JPG, PNG, WebP หรือ PDF ขนาดไม่เกิน 5 MB

กฎ:

- ผู้เรียกต้องเป็นสมาชิกเจ้าของ booking
- booking ต้องมีสถานะ `awaiting_payment`
- `amount` ต้องมากกว่า 0 และมีทศนิยมไม่เกิน 2 ตำแหน่ง
- ตรวจ MIME จากเนื้อไฟล์ ไม่เชื่อเฉพาะนามสกุลหรือ header จาก browser
- บันทึกไฟล์ด้วยชื่อสุ่มในพื้นที่ที่เข้าถึงตรงจากเว็บไม่ได้
- สร้าง payment เป็น `reviewing`
- เปลี่ยน booking เป็น `payment_review` และ `payment_status = reviewing`
- เพิ่ม `booking_status_history`
- การสร้าง payment และเปลี่ยนสถานะทำใน transaction เดียวกัน หากฐานข้อมูลบันทึกไม่สำเร็จต้องลบไฟล์ที่เพิ่งรับไว้

### 7.4 แอดมินดูคิวตรวจการชำระเงิน

ใช้ `GET /v1/admin/review-queue` ที่มีอยู่ โดยรายการ payment ต้องส่ง:

- payment id และเวลาส่ง
- booking public id
- ชื่อสมาชิกและเทรนเนอร์
- วันเวลาและสถานที่นัด
- `quotedPrice` และยอด `amount`
- ส่วนต่างระหว่างราคากับยอดโอนสำหรับแสดงผล
- MIME และ URL ที่มีการตรวจสิทธิ์สำหรับเปิดหลักฐาน

ยอดที่ต่างจากราคาสุดท้ายไม่ถูกปฏิเสธอัตโนมัติ แอดมินเห็นตัวเลขทั้งสองค่าและตัดสินจากหลักฐาน

### 7.5 แอดมินตัดสินการชำระเงิน

ใช้ endpoint เดิม:

- `POST /v1/admin/payments/{id}/approve`
- `POST /v1/admin/payments/{id}/reject`

request body:

```json
{
  "note": "เหตุผลหรือบันทึกการตรวจ"
}
```

กฎ:

- ผู้เรียกต้องเป็นแอดมิน
- payment ต้องเป็น `reviewing` และเป็นรายการล่าสุดที่กำลังตรวจของ booking
- อนุมัติแล้ว payment เป็น `approved`, booking เป็น `confirmed`, `payment_status = approved` และ slot เป็น `booked`
- ไม่อนุมัติแล้ว payment เป็น `rejected`, booking กลับเป็น `awaiting_payment` และ `payment_status = rejected`
- การไม่อนุมัติต้องมี note ที่ไม่ใช่ช่องว่าง
- การอนุมัติใช้ note เป็นทางเลือก
- เพิ่ม `booking_status_history` ทั้งสองกรณี
- ล็อก booking และ payment ก่อนตรวจสถานะ การแก้ทุกตารางทำใน transaction เดียวกัน
- การกดซ้ำหรือข้อมูลหน้าจอล้าสมัยตอบ `409`

### 7.6 ข้อความและไฟล์แนบ

ใช้ endpoint เดิมและขยายให้รองรับ polling กับไฟล์แนบ:

- `GET /v1/chat-rooms/{roomId}/messages?afterId={lastMessageId}`
- `POST /v1/chat-rooms/{roomId}/messages`
- `GET /v1/chat-rooms/{roomId}/messages/{messageId}/attachment`

การส่งข้อความใช้ `multipart/form-data`:

- `message`: ข้อความ ไม่จำเป็นเมื่อมีไฟล์แนบ
- `attachment`: JPG, PNG, WebP หรือ PDF ขนาดไม่เกิน 5 MB ไม่จำเป็นเมื่อมีข้อความ

กฎ:

- ต้องมีข้อความหรือไฟล์อย่างน้อยหนึ่งอย่าง
- ผู้เรียกต้องเป็นสมาชิกหรือเทรนเนอร์ที่ผูกกับ booking ของห้องนั้น
- เปิดส่งข้อความเมื่อ booking ผ่าน `pending_trainer` ไปแล้ว
- booking ที่ `cancelled` เปิดอ่านได้แต่ส่งเพิ่มไม่ได้
- ตรวจ MIME และจัดเก็บไฟล์ด้วยชื่อสุ่มนอก public directory
- endpoint เปิดไฟล์ตรวจทั้ง room ownership และ message ownership
- response ข้อความส่ง id, sender, message, attachment metadata, createdAt และ readAt โดยไม่ส่ง path จริง
- หน้าเว็บ poll ทุกประมาณ 5 วินาทีเมื่อแท็บมองเห็น และหยุดเมื่อออกจากหน้าหรือแท็บถูกซ่อน
- polling ใช้ `afterId` เพื่อลดข้อมูลซ้ำและป้องกันข้อความเด้งกลับไปต้นรายการ

### 7.7 เทรนเนอร์ปิดงาน

ใช้ endpoint เดิม:

`PATCH /v1/bookings/{publicId}/status`

request body:

```json
{
  "status": "completed"
}
```

กฎ:

- ผู้เรียกต้องเป็นเทรนเนอร์เจ้าของ booking
- booking ต้องเป็น `confirmed` และ `payment_status = approved`
- เวลา server ต้องเท่ากับหรือเลย `ends_at`
- เปลี่ยนเป็น `completed` และเพิ่ม `booking_status_history` ใน transaction เดียวกัน
- แอดมินและสมาชิกไม่สามารถใช้ endpoint นี้ปิดงานแทนเทรนเนอร์
- กดซ้ำหรือพยายามปิดก่อนเวลาได้ `409`

### 7.8 สมาชิกเขียนรีวิว

ใช้ `POST /v1/reviews` ที่มีอยู่

request body:

```json
{
  "bookingId": "booking-public-id",
  "rating": 5,
  "comment": "อธิบายประสบการณ์ฝึกจริง"
}
```

กฎ:

- ผู้เรียกต้องเป็นสมาชิกเจ้าของ booking
- booking ต้องเป็น `completed`
- rating เป็นจำนวนเต็ม 1 ถึง 5
- comment ต้องไม่เป็นช่องว่างและมีความยาวตามข้อจำกัดกลางของระบบ
- หนึ่ง booking มีรีวิวได้หนึ่งรายการตาม unique constraint
- รีวิวสร้างเป็น `published` และแสดงในโปรไฟล์เทรนเนอร์ทันที
- การส่งซ้ำตอบ `409`

## 8. ความปลอดภัยของไฟล์

- สลิปและไฟล์แนบไม่อยู่ใน `public/` และไม่เปิด directory listing
- ใช้ชื่อไฟล์สุ่มที่ไม่อ้างชื่อเดิมของผู้ใช้
- เก็บ MIME, ขนาด และชื่อที่ใช้แสดงเป็น metadata ที่ผ่านการทำความสะอาดแล้ว
- ตรวจขนาดทั้งก่อนและหลังรับไฟล์ตามข้อจำกัดของ PHP
- header ตอนดาวน์โหลดกำหนด `Content-Type`, `Content-Length`, `X-Content-Type-Options: nosniff` และรูปแบบ `Content-Disposition` ที่เหมาะสม
- PDF เปิดแบบ inline ได้เมื่อ browser รองรับ ส่วนไฟล์อื่นใช้พฤติกรรมที่ปลอดภัยตาม MIME
- ไม่ส่ง absolute path, stack trace หรือรายละเอียดโฟลเดอร์ XAMPP ใน JSON
- prepared statements ใช้กับ query ทุกจุด และ transaction rollback เมื่อขั้นตอนใดล้มเหลว

## 9. หน้าจอและการใช้งาน

### 9.1 พื้นที่สมาชิก

รายการจองแต่ละรายการแสดงชื่อเทรนเนอร์ วันเวลา สถานที่ ราคาสุดท้าย สถานะการชำระ และการกระทำถัดไป

เมื่อสถานะเป็น `awaiting_payment`:

- แสดงราคาที่ต้องชำระ
- มี label แยกสำหรับยอดที่โอนและไฟล์หลักฐาน
- ก่อนส่งแสดงชื่อไฟล์ ประเภทไฟล์ และปุ่มเปลี่ยนไฟล์
- ระหว่างส่งปิดปุ่มเฉพาะฟอร์มนี้
- เมื่อสำเร็จแสดง "รอตรวจสลิป" และโหลด booking ล่าสุด
- หากสลิปไม่ผ่าน แสดงเหตุผลเดิมเหนือฟอร์มส่งใหม่

เมื่อสถานะเป็น `completed` และยังไม่มีรีวิว:

- แสดงคะแนน 1 ถึง 5 พร้อม label ที่ screen reader อ่านได้
- มีช่องความคิดเห็นและปุ่ม "ส่งรีวิว"
- เมื่อสำเร็จแทนฟอร์มด้วยรีวิวที่เผยแพร่แล้ว

### 9.2 คิวตรวจของแอดมิน

ใช้ queue แบบมีเส้นแบ่ง แต่ละแถวแสดง booking, คู่สัญญา, วันนัด, ราคาสุดท้าย, ยอดโอน, ส่วนต่าง และเวลาส่ง แอดมินเปิดหลักฐานผ่าน endpoint ที่ตรวจสิทธิ์ มีช่อง note และปุ่ม "อนุมัติ" กับ "ไม่อนุมัติ"

เมื่อเลือกไม่อนุมัติแต่ยังไม่กรอกเหตุผล ให้แสดง error ใกล้ช่อง note และไม่ส่ง request เมื่อส่งสำเร็จให้เอารายการออกจากคิวแล้วโหลดข้อมูลล่าสุด

### 9.3 ห้องแชต

เดสก์ท็อปใช้พื้นที่ทำงานสามส่วน:

1. รายการห้องตาม booking เรียงจากข้อความล่าสุด
2. ประวัติข้อความและไฟล์แนบ
3. สรุปเทรนเนอร์ สมาชิก วันเวลา สถานที่ ราคา และสถานะ booking

ข้อความของผู้ใช้ปัจจุบันและคู่สนทนาต่างกันด้วยตำแหน่ง ขอบ และ label ไม่ใช้สีอย่างเดียว ไฟล์แนบแสดงชื่อ ประเภท ขนาด และการกระทำ "เปิดไฟล์" ช่องเขียนข้อความมีปุ่มเลือกไฟล์ ปุ่มเอาไฟล์ออก และปุ่ม "ส่งข้อความ"

เมื่อห้องถูกยกเลิก แสดงประวัติเดิมพร้อมข้อความ "การจองนี้ถูกยกเลิกแล้ว จึงส่งข้อความเพิ่มไม่ได้" หากดึงข้อความไม่สำเร็จให้คงข้อความเดิมบนหน้าจอและแสดงปุ่มลองใหม่

บนมือถือเริ่มจากรายการห้อง เมื่อเลือกห้องจึงเปิดบทสนทนาเต็มหน้าจอ ข้อมูลนัดหมายอยู่ใน disclosure ที่เปิดและปิดได้ ไม่มี horizontal overflow

### 9.4 พื้นที่เทรนเนอร์

ตอนตอบรับคำขอ ฟอร์มต้องมีราคาสุดท้ายพร้อมหน่วยบาท ปุ่มตอบรับยังปิดอยู่จนกรอกราคาถูกต้อง

booking ที่ยืนยันการชำระแล้วแสดงเวลาที่จะปิดงานได้ ปุ่ม "ฝึกเสร็จแล้ว" เปิดเมื่อเลยเวลาสิ้นสุดตามผลจาก server เท่านั้น หากยังไม่ถึงเวลาให้แสดงข้อความบอกเวลาที่ทำรายการได้

## 10. สถานะหน้าจอและภาษา

ทุกพื้นที่ต้องมี loading, empty, success, error, disabled และ stale state ที่บอกขั้นตอนถัดไปได้โดยไม่ต้องเดา ตัวอย่างข้อความหลัก:

- `awaiting_payment`: "รอชำระเงิน"
- `payment_review`: "รอตรวจสลิป"
- payment rejected: "สลิปไม่ผ่าน กรุณาตรวจเหตุผลแล้วส่งใหม่"
- `confirmed`: "ยืนยันการชำระแล้ว"
- `completed`: "ฝึกเสร็จแล้ว"
- duplicate review: "การจองนี้มีรีวิวแล้ว"

ข้อความไม่อ้างว่าระบบตรวจธนาคารอัตโนมัติ ไม่ใช้ถ้อยคำโฆษณา และระบุสาเหตุที่แก้ไขได้เมื่อเกิดข้อผิดพลาด

## 11. Responsive และ accessibility

- ใช้โทเคน ฟอนต์ สี ปุ่ม ฟิลด์ และ status badge จากระบบเดิม
- ตรวจที่ 1280 x 800, 768, 375 และ 320 พิกเซล
- บนหน้าจอแคบ queue และ ledger เรียงหนึ่งคอลัมน์
- label เชื่อมกับ input ทุกช่อง และ error เชื่อมผ่าน `aria-describedby`
- สถานะส่งข้อมูลใช้ `aria-live` อย่างเหมาะสมโดยไม่ประกาศทุก polling cycle
- ห้องแชตรักษาตำแหน่งโฟกัสเมื่อมีข้อความใหม่
- ปุ่มและไฟล์แนบใช้งานด้วย keyboard ได้
- focus ring มองเห็นชัด และสถานะไม่สื่อด้วยสีอย่างเดียว
- รองรับการซูม 200 เปอร์เซ็นต์และ `prefers-reduced-motion`

## 12. การจัดการข้อผิดพลาด

| รหัส | ความหมายใน flow นี้ | พฤติกรรมหน้าเว็บ |
| --- | --- | --- |
| 401 | session หมดอายุหรือยังไม่เข้าสู่ระบบ | แจ้งให้เข้าสู่ระบบใหม่และพาไปหน้า login |
| 403 | บทบาทหรือ ownership ไม่ถูกต้อง | แสดงว่าไม่มีสิทธิ์และไม่ลองส่งซ้ำอัตโนมัติ |
| 404 | ไม่พบ booking, payment, room, message หรือไฟล์ | แจ้งว่าไม่พบข้อมูลและโหลดรายการล่าสุด |
| 409 | สถานะล้าสมัย กดซ้ำ ปิดงานก่อนเวลา หรือรีวิวซ้ำ | คงข้อมูลที่กรอกไว้เมื่อเหมาะสมและ refresh booking |
| 413 | ไฟล์ใหญ่เกินกำหนด | แจ้งขนาดสูงสุด 5 MB ใกล้ช่องไฟล์ |
| 415 | ชนิดไฟล์ไม่รองรับ | แจ้งชนิดไฟล์ที่รับได้ |
| 422 | ราคา ยอดโอน note คะแนน หรือข้อความไม่ถูกต้อง | แสดง error ใกล้ field ที่ต้องแก้ |
| 500 หรือเครือข่าย | PHP, MySQL หรือ XAMPP ขัดข้อง | คงข้อมูลบนหน้า แสดงปุ่มลองใหม่ และไม่แสดงผลสำเร็จปลอม |

## 13. การตรวจข้อมูลใน phpMyAdmin

เพิ่มสคริปต์ตรวจ flow สำหรับข้อมูลทดสอบหนึ่ง booking โดยสคริปต์ต้อง:

1. รับ booking public id หรือใช้ id ที่สร้างจาก smoke test
2. แสดง booking และสถานะล่าสุด
3. แสดงประวัติทั้งหมดจาก `booking_status_history` ตามเวลา
4. แสดง payment ทุกครั้ง รวมรายการที่ถูกปฏิเสธและรายการที่ผ่าน
5. แสดง chat room และ messages พร้อม metadata ของไฟล์แนบ โดยไม่พิมพ์เนื้อไฟล์
6. แสดง review และสถานะเผยแพร่
7. ตรวจความสัมพันธ์ของ foreign key และรายงานรายการที่ขาด
8. จบด้วยผลผ่านหรือไม่ผ่าน พร้อม id ที่ใช้เปิดดูใน phpMyAdmin

README ฝั่ง backend ต้องมีขั้นตอนเปิด phpMyAdmin เลือกฐานข้อมูล `fitconnect` และตรวจหกตารางด้วย booking id เดียวกัน ตัวอย่าง query ใช้ prepared input ในสคริปต์ ส่วนข้อความ SQL สำหรับตรวจด้วยมือระบุ placeholder ชัดเจนเพื่อไม่ให้ผู้ใช้เผลอตรวจคนละ booking

## 14. กลยุทธ์การทดสอบ

### 14.1 กฎฝั่ง PHP/API

ทดสอบอย่างน้อย:

- เทรนเนอร์ตอบรับ booking ของตนพร้อมราคาที่ถูกต้องได้
- ราคาว่าง ศูนย์ ติดลบ หรือรูปแบบไม่ถูกต้องได้ `422`
- เทรนเนอร์อื่นแก้ราคาและสถานะไม่ได้
- สมาชิกเจ้าของ booking ส่งยอดและสลิปชนิดที่อนุญาตได้
- ผู้ใช้อื่นส่งสลิปแทนไม่ได้
- ไฟล์ใหญ่เกินกำหนดหรือ MIME ไม่ตรงถูกปฏิเสธ
- ส่งสลิปสำเร็จแล้ว payment, booking และ history ถูกบันทึกครบ
- แอดมินอนุมัติแล้ว payment, booking, slot และ history เปลี่ยนพร้อมกัน
- แอดมินไม่อนุมัติโดยไม่มีเหตุผลได้ `422`
- ไม่อนุมัติแล้วส่งสลิปใหม่ได้ โดยยังเก็บ payment เดิม
- เฉพาะคู่สนทนาอ่านและส่งข้อความในห้องได้
- ข้อความอย่างเดียว ไฟล์อย่างเดียว และข้อความพร้อมไฟล์ส่งได้
- ห้องที่ยกเลิกอ่านได้แต่ส่งข้อความไม่ได้
- ผู้ที่ไม่เกี่ยวข้องเปิดไฟล์แนบไม่ได้
- เทรนเนอร์ปิดงานก่อนเวลาไม่ได้ และปิดหลังเวลาได้
- สมาชิกรีวิว booking ที่ completed ได้หนึ่งครั้ง
- สมาชิกอื่น รีวิวก่อนจบงาน และรีวิวซ้ำไม่ได้

### 14.2 Flow ครบวงจร

ทดสอบด้วยบัญชีสมาชิก เทรนเนอร์ และแอดมิน:

1. เทรนเนอร์ตอบรับคำขอพร้อมราคาสุดท้าย
2. สมาชิกเปิดห้องแชต ส่งข้อความ รูป และ PDF
3. สมาชิกส่งยอดโอนและสลิป
4. แอดมินไม่อนุมัติพร้อมเหตุผล
5. สมาชิกเห็นเหตุผลและส่งสลิปใหม่
6. แอดมินอนุมัติ
7. เทรนเนอร์ปิดงานหลังเลยเวลานัด
8. สมาชิกให้คะแนนและเขียนรีวิว
9. สคริปต์ audit ยืนยันว่าทุกตารางเชื่อมกับ booking เดียวกัน

### 14.3 คุณภาพหน้าเว็บ

- lint
- TypeScript typecheck
- production build
- PHP syntax check และ test suite
- API smoke test กับ XAMPP/MySQL จริง
- browser test สำหรับสมาชิก เทรนเนอร์ และแอดมิน
- ตรวจ responsive, keyboard, focus, loading, empty, error, stale data และ API unavailable
