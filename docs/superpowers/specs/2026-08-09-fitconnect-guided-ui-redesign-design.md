# FitConnect Guided UI Redesign

วันที่: 9 สิงหาคม 2026
สถานะ: อนุมัติทิศทางการออกแบบแล้ว รอผู้ใช้ตรวจเอกสารก่อนจัดทำแผน implementation

## 1. เป้าหมาย

ปรับ UI ของ FitConnect ให้สะอาด เป็นมิตร และเข้าใจง่ายขึ้น โดยนำหลักการจาก Scisiam มาใช้กับบริบทสุขภาพและการออกกำลังกาย ภายใต้แนวทาง **Guided FitConnect**: ผู้ใช้เห็นภาพรวมก่อน ทำงานทีละขั้น และเปิดรายละเอียดเมื่อจำเป็น

การปรับครั้งนี้เปลี่ยนเฉพาะการจัดลำดับข้อมูล รูปแบบการนำเสนอ การนำทาง และ visual system ไม่เพิ่มความสามารถทางธุรกิจหรือเปลี่ยนขั้นตอนระบบที่กำหนดไว้ในเอกสารบทที่ 1 และบทที่ 3

## 2. ขอบเขตที่ต้องรักษา

ฟังก์ชันเดิมต้องยังทำงานครบ:

- สมัครสมาชิก เข้าสู่ระบบ และแสดงข้อมูลตามบทบาท
- สมาชิกค้นหา กรอง และดูโปรไฟล์เทรนเนอร์
- แสดงความเชี่ยวชาญ ใบรับรอง ราคา รีวิว และตารางว่าง
- สมาชิกส่งคำขอจองและเทรนเนอร์ตอบรับหรือปฏิเสธ
- สมาชิกอัปโหลดสลิปและแอดมินตรวจหลักฐานด้วยตนเอง
- สมาชิกและเทรนเนอร์แชตกันตามการจอง
- สมาชิกเขียนรีวิวหลังจบการฝึก
- เทรนเนอร์จัดการใบสมัคร โปรไฟล์ ตารางว่าง คำขอจอง ลูกค้า รีวิว และข้อมูลสรุปที่มีอยู่
- แอดมินตรวจใบสมัครเทรนเนอร์ ใบรับรอง การชำระเงิน ผู้ใช้ การจอง และรายงานที่มีอยู่
- รองรับจังหวัดอื่นในอนาคต โดยไม่ออกแบบหน้าจอให้ผูกกับสกลนครเพียงจังหวัดเดียว

## 3. สิ่งที่ไม่อยู่ในขอบเขต

งาน redesign นี้จะไม่เพิ่ม AI แนะนำเทรนเนอร์, GPS tracking, วิดีโอคอล, subscription, payment gateway อัตโนมัติ, gamification, ฟีดสังคม หรือโครงสร้างฐานข้อมูลใหม่ การเลือก “เป้าหมายการฝึก” บนหน้าแรกเป็นเพียงทางลัดไปยังประเภทการฝึกที่ระบบมีอยู่ ไม่ใช่ recommendation engine

## 4. หลักการออกแบบ

1. **Overview before detail** — หน้าแรกอธิบายบริการและเส้นทางใช้งานก่อนเข้าสู่หน้าค้นหาแบบละเอียด
2. **One screen, one purpose** — แต่ละช่วงหน้าจอมีงานหลักหนึ่งอย่างและ CTA หลักหนึ่งรายการ
3. **Progressive disclosure** — ตัวกรอง หลักฐาน ตาราง ประวัติ และข้อมูลรองเปิดเมื่อผู้ใช้ร้องขอ
4. **Next action first** — Dashboard แสดงสิ่งที่ผู้ใช้ควรทำต่อก่อนสถิติหรือประวัติ
5. **Same facts, different priority** — สมาชิก เทรนเนอร์ และแอดมินเห็นข้อเท็จจริงการจองชุดเดียวกัน แต่เรียงตามงานของบทบาท
6. **Honest operations** — การตรวจเอกสารและสลิปต้องสื่อว่าเป็นการตรวจโดยแอดมิน ไม่อ้างว่าอัตโนมัติ
7. **Thai-first and mobile-first** — ภาษาไทยต้องอ่านง่าย ปุ่มแตะสะดวก และข้อมูลสำคัญไม่พึ่งตารางกว้างบนมือถือ

## 5. โครงสร้างหน้าแรก

หน้าแรกเปลี่ยนจาก workbench ที่แสดงตัวกรอง รายชื่อ หลักฐาน ตารางเวลา และแถบจองพร้อมกัน เป็นหน้าแนะนำบริการตามลำดับ:

1. Hero สั้น พร้อมคำอธิบายคุณค่าของ FitConnect และปุ่ม `ค้นหาเทรนเนอร์`
2. ประเภทหรือเป้าหมายการฝึกที่ดึงจาก reference data เดิม ผู้ใช้เลือกแล้วเข้าสู่หน้าค้นหาที่ตั้งค่าตัวกรองให้
3. เทรนเนอร์แนะนำ 3–4 คน แสดงเพียงรูป ชื่อ ความเชี่ยวชาญหลัก จังหวัด ราคาเริ่มต้น และสถานะตรวจสอบ
4. ขั้นตอนการใช้งาน: เลือกเทรนเนอร์ → เลือกเวลา → ส่งคำขอ → อัปโหลด/ตรวจสลิป → เริ่มฝึกและรีวิว
5. ส่วนความน่าเชื่อถือ อธิบายการตรวจใบรับรอง การตรวจสลิป และรีวิวหลังการฝึกด้วยข้อความจริง
6. CTA ท้ายหน้า `ดูเทรนเนอร์ทั้งหมด`

ตัวกรองละเอียด หลักฐานเต็ม ตารางว่าง และข้อมูลการจองจะอยู่ที่ `/trainers` และหน้าโปรไฟล์เทรนเนอร์ ไม่ซ้ำบนหน้าแรก

## 6. โครง Dashboard ตามบทบาท

ทุก Dashboard ใช้โครงร่วมกัน: คำทักทายและสถานะสั้น → การ์ด “สิ่งที่ต้องทำต่อ” → รายการล่าสุด 2–3 รายการ → ลิงก์ดูทั้งหมด → ข้อมูลรองในแท็บหรือ disclosure

### สมาชิก

- Next action เปลี่ยนตามสถานะจริง: เริ่มค้นหา รอเทรนเนอร์ตอบรับ อัปโหลดสลิป รอการตรวจ นัดหมาย แชต หรือเขียนรีวิว
- แสดงการจองล่าสุดแบบสรุป ไม่เปิด history ทั้งหมดตั้งแต่แรก
- ข้อความใหม่และสถานะชำระเงินเป็นข้อมูลรองที่กดเข้าสู่หน้ารายละเอียดได้

### เทรนเนอร์

- ให้คำขอจองที่รอตอบรับเป็นงานสำคัญที่สุดเมื่อมีรายการ
- แสดงตารางวันนี้และช่วงว่างถัดไปแบบสั้น
- แสดงสถานะการสมัครหรือการอนุมัติเฉพาะเมื่อเกี่ยวข้อง
- รีวิว รายรับ และประวัติเป็นข้อมูลรอง ไม่แข่งขันกับงานที่ต้องตอบ

### แอดมิน

- แสดงคิวตรวจใบสมัครเทรนเนอร์และคิวตรวจสลิปเป็นงานหลัก
- จำนวนรายการใช้เป็นตัวช่วยตัดสินใจ ไม่สร้างแผงสถิติหลายใบโดยไม่มี action
- ตารางเต็มแสดงหลังเลือกหมวดงาน
- ผู้ใช้ การจอง ประวัติ และรายงานอยู่ใน navigation รอง

## 7. Navigation

- เดสก์ท็อปแสดงปลายทางหลักที่ใช้บ่อย ส่วนงานเฉพาะบทบาทอยู่ในเมนูบัญชีหรือแถบนำทางที่เรียบ
- มือถือใช้ bottom navigation ไม่เกิน 4 รายการ: หน้าแรก, งานหลักของบทบาท, แชต และบัญชี โดยชื่อรายการ “งานหลัก” เปลี่ยนเป็นคำที่ตรงกับบทบาท เช่น การจองหรือคิวตรวจ
- Active state ต้องสื่อด้วยสี ไอคอน และข้อความ ไม่ใช้สีเพียงอย่างเดียว
- หลีกเลี่ยงการแสดงเมนูทุกความสามารถพร้อมกัน

## 8. Visual System

บุคลิกคือ **Friendly Fitness Guidance**: สว่าง เป็นมิตร เชื่อถือได้ และมีพลังอย่างควบคุม

- พื้นหลังใช้ neutral เทาอมเขียวอ่อน
- พื้นผิวสำคัญใช้สีขาว ขอบอ่อน และรัศมี 16–20px
- เขียวป่าเป็นสีโครงสร้างสำหรับหัวข้อ navigation และพื้นที่สร้างความน่าเชื่อถือ
- เขียวมะนาวสงวนไว้สำหรับ CTA หลัก รายการที่เลือก และ focus ที่จำเป็น
- สี success, warning และ error ใช้ตามความหมายจริงเท่านั้น
- ลดเส้นตารางและเส้นแบ่งเข้ม ใช้ระยะห่าง สีพื้น และ heading แบ่งกลุ่มแทน
- เงาใช้เฉพาะพื้นผิวที่ลอย เปิด หรือโต้ตอบ ไม่ใส่ทุกการ์ด
- ไอคอนใช้ตระกูลเดียวกัน มี label เมื่อความหมายไม่ชัด และไม่ใช้ภาพตกแต่งที่ไม่ช่วยงาน

Typography ใช้ Bai Jamjuree สำหรับภาษาไทยและเนื้อหาทั่วไป Chakra Petch ใช้จำกัดกับ wordmark, heading สำคัญ หรือตัวเลขที่ต้องการบุคลิกเชิงกีฬา เพื่อลดความแข็งและความหนาแน่นของหน้าปัจจุบัน

## 9. Component Patterns

- **NextActionCard**: งานถัดไปหนึ่งรายการ พร้อมสถานะ คำอธิบายสั้น และ CTA เดียว
- **CompactSummaryCard**: สรุปการจอง ข้อความ ตาราง หรือคิวตรวจ โดยแสดงข้อมูลไม่เกินที่จำเป็นต่อการตัดสินใจ
- **TrainerPreviewCard**: รูป ชื่อ ความเชี่ยวชาญหลัก จังหวัด ราคาเริ่มต้น สถานะตรวจสอบ และ CTA ไปโปรไฟล์
- **DisclosureSection**: ใช้กับตัวกรอง หลักฐาน ใบรับรอง ประวัติ และข้อมูลรอง
- **StatusBadge**: คงข้อความสถานะมาตรฐานและไอคอนประกอบจากระบบเดิม
- **EmptyState**: บอกว่าไม่มีอะไร เหตุผลที่เป็นไปได้ และขั้นตอนถัดไป
- **Loading/Error/Success**: ใช้รูปแบบและภาษาเดียวกันทุกบทบาท

หลีกเลี่ยง nested cards หลายชั้น การ์ดสถิติจำนวนมาก และข้อมูลเดียวกันที่ซ้ำทั้งหน้า

## 10. Interaction และ Data Flow

การเปลี่ยนหน้าและการเปิดรายละเอียดต้องใช้ข้อมูล/API เดิม การ redesign ไม่เปลี่ยน contract ระหว่าง Next.js กับ PHP/MySQL

- การเลือกประเภทการฝึกบนหน้าแรกส่งค่าไปหน้าค้นหาเป็น filter ที่ระบบรองรับ
- การ์ดสรุปเชื่อมไปยังรายละเอียดจริงของ booking, payment, chat, trainer application หรือ review
- Dashboard คำนวณ next action จากสถานะที่มีอยู่ ไม่สร้างสถานะใหม่
- ตัวกรองละเอียดเริ่มต้นปิดบนพื้นที่แคบและจำค่าที่เลือกในระหว่างเส้นทางค้นหาเท่าที่ระบบปัจจุบันรองรับ
- งาน async ต้องมี loading, success, error และ disabled state โดยไม่ล้างข้อมูลที่ผู้ใช้กรอกเมื่อเกิดข้อผิดพลาด

## 11. Responsive และ Accessibility

- 320–414px: หนึ่งคอลัมน์, bottom navigation, CTA อยู่ใน thumb zone, ตารางเปลี่ยนเป็นรายการสรุป
- 768px: ใช้หนึ่งหรือสองคอลัมน์ตามเนื้อหา โดยไม่ย่อ workbench เดสก์ท็อปลงมาตรง ๆ
- เดสก์ท็อป: จำกัดความกว้างเนื้อหาและใช้พื้นที่ว่างสร้างลำดับชั้น ไม่เติมทุกพื้นที่ด้วยแผง
- Touch target อย่างน้อย 44px, focus-visible ชัดเจน, heading semantic, label ครบ และสถานะไม่พึ่งสี
- รองรับ keyboard flow, reduced motion, zoom 200% และภาษาไทยยาวโดยไม่เกิด horizontal overflow

## 12. การตรวจสอบ

ตรวจเส้นทางหน้าแรก สมาชิก เทรนเนอร์ แอดมิน ค้นหา โปรไฟล์ จอง ชำระเงิน แชต และรีวิว โดยใช้ข้อมูลจริงจาก demo/API ที่มีอยู่

- Visual checks: 1280×800, 768px, 414px, 375px และ 320px
- ตรวจ empty, loading, error, disabled, success และข้อมูลข้อความยาว
- ตรวจ keyboard navigation, focus order, screen-reader labels และ contrast ตาม WCAG 2.2 AA
- รันทดสอบ frontend, lint, typecheck และ production build
- รันทดสอบ PHP/API เดิมเพื่อยืนยันว่า redesign ไม่กระทบ business flow และข้อมูลใน MySQL

## 13. ลำดับการดำเนินงานที่แนะนำ

1. สร้าง/ปรับ tokens และ component primitives ที่ใช้ร่วมกัน
2. ปรับ site header, role navigation และ mobile navigation
3. แยกหน้าแรกออกจาก trainer discovery workbench
4. ปรับ Dashboard สมาชิก เทรนเนอร์ และแอดมินด้วย shared patterns
5. ปรับหน้าค้นหา โปรไฟล์ จอง ชำระเงิน และแชตให้ใช้ visual system เดียวกัน
6. ตรวจ responsive, accessibility, states และ regression ทั้งระบบ

การแบ่งลำดับนี้ช่วยให้เห็นผลเรื่องความรกตั้งแต่หน้าแรกและ navigation ก่อน แล้วค่อยขยายระบบภาพไปยังหน้าธุรกรรมโดยไม่เปลี่ยน backend หรือฐานข้อมูล
