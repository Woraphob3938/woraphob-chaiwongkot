# FitConnect: การอนุมัติเทรนเนอร์ ตารางว่าง และคำขอจอง

วันที่: 1 สิงหาคม 2026

สถานะ: ข้อตกลงการออกแบบได้รับการยืนยันแล้ว และรอตรวจทานสเปกฉบับเขียน

ขอบเขต: ขั้นตอนที่ 3–6 ของระบบ FitConnect

## 1. เป้าหมาย

ทำให้ขั้นตอนหลักตั้งแต่การตรวจใบสมัครเทรนเนอร์จนถึงการตอบรับคำขอจองใช้งานกับข้อมูลจริงได้ครบวงจร:

1. แอดมินเปิดดูหลักฐานและอนุมัติหรือปฏิเสธเทรนเนอร์
2. เทรนเนอร์ที่ได้รับอนุมัติสร้างและลบช่วงเวลาว่างของตนเอง
3. สมาชิกค้นหาเทรนเนอร์ เลือกช่วงเวลาที่ยังว่าง และส่งคำขอจอง
4. เทรนเนอร์ตอบรับหรือปฏิเสธคำขอ
5. ทุกการเปลี่ยนสถานะสำคัญถูกบันทึกและป้องกันการจองชนกัน

ระบบยังคงใช้สถาปัตยกรรมปัจจุบัน ได้แก่ Next.js สำหรับหน้าเว็บ, PHP API ภายใต้ XAMPP และ MySQL โดยไม่เปลี่ยนเทคโนโลยีหลักหรือสร้างระบบใหม่ซ้ำซ้อน

## 2. สิ่งที่อยู่นอกขอบเขต

- การชำระเงินหลังเทรนเนอร์ตอบรับ
- การยกเลิกโดยสมาชิกหลังเข้าสู่ขั้นตอนชำระเงิน
- ตารางแบบเกิดซ้ำอัตโนมัติ เช่น ทุกวันจันทร์
- การซิงก์กับ Google Calendar หรือปฏิทินภายนอก
- การแจ้งเตือนผ่านอีเมล, LINE หรือ push notification
- การขยายหรือเปลี่ยน schema ฐานข้อมูล เพราะตารางและสถานะที่มีอยู่รองรับงานนี้แล้ว

## 3. สภาพระบบปัจจุบัน

ฐานข้อมูลมีตารางหลักที่ต้องใช้แล้ว ได้แก่ `trainer_profiles`, `trainer_certificates`, `availability_slots`, `bookings`, `booking_status_history` และ `chat_rooms`

API ปัจจุบันมีความสามารถบางส่วนแล้ว:

- ส่งใบสมัครเทรนเนอร์
- ดูคิวตรวจของแอดมินและบันทึกผลอนุมัติ
- สร้างการจองพร้อมล็อกช่วงเวลา
- เปลี่ยนสถานะการจอง
- แสดงรายชื่อเทรนเนอร์

ส่วนที่ต้องเติมหรือทำให้รัดกุมคือ รายละเอียดไฟล์ในคิวตรวจ, API จัดการตารางว่าง, สิทธิ์และ state transition ของคำขอจอง, การคืนช่วงเวลาเมื่อปฏิเสธ และการนำข้อมูลสาธิตออกจากเส้นทางจองจริง

## 4. สถาปัตยกรรมและขอบเขตความรับผิดชอบ

### 4.1 PHP API

PHP API เป็นแหล่งความจริงเดียวของสิทธิ์ สถานะ และกฎทางธุรกิจ หน้าเว็บมีหน้าที่แสดงผลและช่วยตรวจข้อมูลเบื้องต้นเท่านั้น กฎสำคัญทั้งหมดต้องตรวจซ้ำใน API

งานเขียนหลายตารางที่ต้องสำเร็จหรือยกเลิกพร้อมกันใช้ MySQL transaction ได้แก่:

- อนุมัติหรือปฏิเสธเทรนเนอร์และใบรับรอง
- สร้างคำขอจองและยึดช่วงเวลา
- ตอบรับหรือปฏิเสธคำขอจองและปรับสถานะช่วงเวลา

### 4.2 Next.js

หน้าเว็บใช้ component และ dashboard ตามบทบาทที่มีอยู่ ไม่สร้างระบบนำทางชุดใหม่ งานหลักคือเชื่อมหน้าปัจจุบันกับ API จริง เพิ่มสถานะกำลังโหลด/ผิดพลาด และเอาข้อมูลสาธิตออกจากขั้นตอนที่สามารถสร้างหรือแก้ข้อมูลจริง

### 4.3 MySQL

ใช้ schema ปัจจุบันโดยไม่มี migration ในงานนี้:

- `trainer_profiles.approval_status` เก็บ `pending`, `approved`, `rejected`
- `trainer_certificates.review_status` เก็บผลตรวจของหลักฐาน
- `availability_slots.state` เก็บ `available`, `held`, `booked`, `blocked`
- `bookings.status` ใช้ `pending_trainer`, `awaiting_payment`, `cancelled` ในขั้นตอนนี้
- `booking_status_history` เก็บประวัติทุกการเปลี่ยนสถานะการจอง

## 5. สิทธิ์ของแต่ละบทบาท

| การกระทำ | สมาชิก | เทรนเนอร์ | แอดมิน |
| --- | --- | --- | --- |
| ดูเทรนเนอร์ที่อนุมัติแล้ว | ได้ | ได้ | ได้ |
| ส่งคำขอจอง | ได้ | ไม่ได้ | ไม่ได้ |
| ดูคำขอของตนเอง | ได้ | ได้เฉพาะคำขอของตน | ได้ตามเครื่องมือดูแลระบบเดิม |
| สร้าง/ลบตารางว่าง | ไม่ได้ | ได้เมื่ออนุมัติแล้ว | ไม่ได้ |
| ตอบรับ/ปฏิเสธคำขอ | ไม่ได้ | ได้เฉพาะคำขอของตน | ไม่ได้ |
| เปิดไฟล์ใบรับรอง | ไม่ได้ | ไม่ได้ผ่านเส้นทางแอดมิน | ได้ |
| อนุมัติ/ปฏิเสธเทรนเนอร์ | ไม่ได้ | ไม่ได้ | ได้ |

ผู้ใช้ที่ไม่เข้าสู่ระบบได้รับ `401`; ผู้ใช้ที่เข้าสู่ระบบแต่ไม่มีสิทธิ์หรือเทรนเนอร์ที่ยังไม่อนุมัติได้รับ `403`

## 6. API contract

ทุก endpoint ใช้ response envelope และรูปแบบ error เดิมของโครงการ พร้อมรหัส HTTP ตามหัวข้อ 10

### 6.1 ข้อมูลเทรนเนอร์เจ้าของบัญชี

`GET /v1/trainer/me`

สิทธิ์: เทรนเนอร์ที่เข้าสู่ระบบ

ผลลัพธ์ประกอบด้วย:

- ข้อมูลโปรไฟล์และ `approvalStatus`
- `approvalNote` เมื่อถูกปฏิเสธ
- สรุปใบรับรองและสถานะตรวจ
- ช่วงเวลาว่างของเทรนเนอร์ในอนาคต เรียงจากใกล้ไปไกล

เทรนเนอร์ที่ยังไม่ได้รับอนุมัติยังอ่านข้อมูลสถานะของตนได้ แต่สร้างตารางว่างไม่ได้

### 6.2 สร้างช่วงเวลาว่าง

`POST /v1/availability-slots`

สิทธิ์: เทรนเนอร์ที่ `approval_status = approved` และบัญชี active

request body:

```json
{
  "startsAt": "2026-08-10T02:00:00.000Z",
  "endsAt": "2026-08-10T03:00:00.000Z"
}
```

กฎ:

- เวลาเริ่มต้องอยู่ในอนาคต
- เวลาสิ้นสุดต้องมากกว่าเวลาเริ่ม
- เวลาเริ่มต้องไม่ไกลเกินสองเดือนนับจากเวลาปัจจุบัน
- ช่วงเวลาใหม่ห้ามทับกับทุก slot ของเทรนเนอร์ที่ยังมีผลอยู่ ไม่ใช่เพียงชนเวลาเริ่มตรงกัน
- เมื่อสำเร็จสร้าง slot เป็น `available`

API ล็อกแถว `trainer_profiles` ของเจ้าของภายใน transaction ก่อนตรวจช่วงเวลาทับซ้อนและ insert เพื่อทำให้คำขอสร้างพร้อมกันถูกประมวลผลตามลำดับ

### 6.3 ลบช่วงเวลาว่าง

`DELETE /v1/availability-slots/{id}`

สิทธิ์: เทรนเนอร์เจ้าของ slot ที่ได้รับอนุมัติแล้ว

ลบได้เฉพาะ slot ที่:

- เป็นของผู้ใช้ปัจจุบัน
- อยู่ในอนาคต
- มีสถานะ `available`

slot ที่ถูกยึดหรือจองแล้วห้ามลบและตอบ `409`

### 6.4 คิวตรวจเทรนเนอร์ของแอดมิน

ปรับ `GET /v1/admin/review-queue` ให้รายการเทรนเนอร์แต่ละคนมีข้อมูลใบรับรอง:

```json
{
  "certificates": [
    {
      "id": 12,
      "name": "Personal Trainer Certificate",
      "issuer": "Example Academy",
      "submittedAt": "2026-07-30T07:00:00.000Z",
      "fileUrl": "/v1/admin/files/certificate/12"
    }
  ]
}
```

`fileUrl` เป็นเส้นทางที่มีอยู่แล้วและต้องตรวจสิทธิ์แอดมินทุกครั้ง ห้ามส่ง path จริงของไฟล์บนเครื่องแม่ข่ายให้ browser

### 6.5 ตัดสินใบสมัครเทรนเนอร์

ใช้ endpoint ที่มีอยู่:

- `POST /v1/admin/trainers/{id}/approve`
- `POST /v1/admin/trainers/{id}/reject`

request body:

```json
{
  "note": "ข้อความประกอบการพิจารณา"
}
```

กฎ:

- ตัดสินได้เฉพาะใบสมัครสถานะ `pending`
- การกดซ้ำหรือข้อมูลบนหน้าจอล้าสมัยตอบ `409`
- อนุมัติแล้ว `trainer_profiles.approval_status = approved` และใบรับรองของใบสมัครเป็น `verified`
- ปฏิเสธแล้วโปรไฟล์และใบรับรองเป็น `rejected` พร้อมบันทึก note, ผู้ตรวจ และเวลาตรวจ
- note เป็นทางเลือกตอนอนุมัติ แต่จำเป็นตอนปฏิเสธ เพื่อให้เทรนเนอร์รู้สิ่งที่ต้องแก้
- การแก้โปรไฟล์และใบรับรองทำใน transaction เดียวกัน

### 6.6 รายชื่อและรายละเอียดเทรนเนอร์สำหรับสมาชิก

ปรับ endpoint สาธารณะที่มีอยู่:

- `GET /v1/trainers`
- `GET /v1/trainers/{publicId}`

ทั้งสองเส้นทางส่งเฉพาะเทรนเนอร์ที่อนุมัติแล้วและบัญชี active เท่านั้น รายละเอียดเทรนเนอร์ส่งเฉพาะ slot อนาคตที่มีสถานะ `available`; ไม่เปิดเผย slot ที่ `held`, `booked` หรือ `blocked`

การค้นหาจังหวัดและประเภทการฝึกยังใช้ข้อมูลจริงจาก API และต้องรองรับจังหวัดอื่นในอนาคต ไม่ผูกระบบไว้กับจังหวัดสกลนคร

### 6.7 สร้างคำขอจอง

ใช้ `POST /v1/bookings` ที่มีอยู่ โดยหน้าเว็บส่ง trainer และ slot ที่โหลดจาก API จริง

กฎฝั่ง API:

- ผู้ส่งต้องเป็นสมาชิก
- trainer ต้องอนุมัติแล้วและบัญชี active
- slot ต้องเป็นของ trainer ที่เลือก อยู่ในอนาคต และเป็น `available`
- ล็อกแถว slot ด้วย `SELECT ... FOR UPDATE`
- สร้าง booking เป็น `pending_trainer`
- เปลี่ยน slot เป็น `held`
- เพิ่ม `booking_status_history`
- สร้างห้องแชตตามพฤติกรรมเดิม
- ทุกการเปลี่ยนแปลงอยู่ใน transaction เดียวกัน

ถ้ามีสมาชิกสองคนจอง slot เดียวกันพร้อมกัน คำขอที่เข้าถึง slot ตอนยังว่างสำเร็จเพียงหนึ่งรายการ อีกคำขอได้ `409`

### 6.8 รายการจองตามบทบาท

ปรับ `GET /v1/bookings` ให้ผลลัพธ์ตามบทบาท:

- สมาชิกเห็น booking ของตนเอง
- เทรนเนอร์เห็น booking ที่ผูกกับ trainer profile ของตนเอง

รายการสำหรับเทรนเนอร์ต้องมีอย่างน้อย public id ของ booking, ชื่อสมาชิก, เวลาเริ่ม/สิ้นสุด, สถานที่, note ของสมาชิก และสถานะปัจจุบัน

### 6.9 เทรนเนอร์ตอบคำขอ

ใช้ `PATCH /v1/bookings/{publicId}/status` ที่มีอยู่ โดยรับเฉพาะ action ที่หน้าจอนี้ต้องใช้:

```json
{
  "status": "awaiting_payment"
}
```

หรือ

```json
{
  "status": "cancelled"
}
```

กฎ:

- ผู้เรียกต้องเป็นเทรนเนอร์เจ้าของ booking
- สถานะเดิมต้องเป็น `pending_trainer`
- ล็อก booking ภายใน transaction ก่อนตรวจสถานะ
- ตอบรับ: booking เป็น `awaiting_payment` และ slot ยังเป็น `held`
- ปฏิเสธ: booking เป็น `cancelled` และ slot กลับเป็น `available` ทันที
- ทั้งสองกรณีเพิ่ม `booking_status_history`
- การกดซ้ำหรือสถานะล้าสมัยตอบ `409`

การเปลี่ยนสถานะในขั้นตอนชำระเงินและจบงานยังคงเป็นความรับผิดชอบของ endpoint/บทบาทเดิม และห้ามเปิดให้เทรนเนอร์ข้ามจาก `pending_trainer` ไปสถานะอื่นนอกเหนือจากสองสถานะข้างต้น

## 7. State transitions

### 7.1 ใบสมัครเทรนเนอร์

```text
pending ──approve──> approved
   └─────reject────> rejected
```

การออกแบบรอบนี้ไม่อนุญาตให้ตัดสินซ้ำหรือเปลี่ยนจาก approved กลับเป็น pending ผ่านหน้าคิวตรวจ

### 7.2 ช่วงเวลาว่างและคำขอจอง

```text
slot: available
  └─ สมาชิกส่งคำขอสำเร็จ ─> held
       ├─ เทรนเนอร์ตอบรับ ─> held และ booking: awaiting_payment
       └─ เทรนเนอร์ปฏิเสธ ─> available และ booking: cancelled
```

เส้นทางต่อจาก `awaiting_payment` เช่น การตรวจชำระเงินและเปลี่ยน slot เป็น `booked` อยู่นอกขอบเขตงานนี้ แต่พฤติกรรมเดิมต้องไม่เสียหาย

## 8. เวลาและเขตเวลา

- หน้าเว็บแสดงเวลาเป็นเขตเวลาไทยและใช้รูปแบบภาษาไทยตาม component เดิม
- ช่อง `datetime-local` ถูกแปลงด้วย JavaScript เป็น ISO UTC ก่อนส่ง API
- API แปลงและบันทึกเวลาเป็น UTC ใน MySQL
- การตรวจ “อนาคต” และ “ไม่เกินสองเดือน” ใช้เวลาของ server ใน UTC
- API ส่งเวลาแบบ ISO 8601 พร้อม `Z` เพื่อไม่ให้ browser ตีความเป็นเวลา local ซ้ำ

## 9. ประสบการณ์ใช้งาน

### 9.1 หน้าแอดมิน

- แสดงแถวใบสมัครที่รอตรวจ พร้อมชื่อ จังหวัด วันที่ส่ง และรายการใบรับรอง
- กดเปิด PDF ในแท็บใหม่ผ่านเส้นทางแอดมิน
- มีช่อง note และปุ่มอนุมัติ/ปฏิเสธในแถวเดียวกัน
- ระหว่างส่งคำขอ ปิดปุ่มของแถวนั้นเพื่อป้องกันการกดซ้ำ
- เมื่อสำเร็จ ลบแถวจากหน้าจอแล้วโหลดคิวล่าสุดอีกครั้ง

### 9.2 หน้าเทรนเนอร์

ใช้หน้าเดียวแบ่งเป็นสามส่วน:

1. สถานะการอนุมัติและเหตุผลเมื่อถูกปฏิเสธ
2. ฟอร์มสร้างช่วงเวลาว่างและรายการ slot ในอนาคต
3. คิวคำขอจอง พร้อมข้อมูลสมาชิก เวลา สถานที่ note และปุ่มตอบรับ/ปฏิเสธ

เทรนเนอร์ที่ยังไม่อนุมัติเห็นสถานะและเหตุผลได้ แต่ส่วนสร้างตารางถูกปิดพร้อมคำอธิบายที่ชัดเจน

### 9.3 หน้าสมาชิก

- ค้นหาจากรายชื่อเทรนเนอร์จริงตามจังหวัดและประเภทการฝึก
- เลือกเทรนเนอร์แล้วโหลด slot ที่ว่างจาก API
- สรุป trainer, เวลา, สถานที่ และ note ก่อนยืนยัน
- ไม่มีการ fallback ไปข้อมูลสาธิตเมื่อกำลังสร้าง booking จริง
- เมื่อสำเร็จไปหน้าสมาชิกและแสดง booking ใหม่

### 9.4 Responsive และ accessibility

- บนมือถือ ส่วนควบคุมและรายการเรียงเป็นหนึ่งคอลัมน์
- ปุ่มและลิงก์ใช้ label ที่บอกการกระทำชัดเจน
- form field มี label ที่เชื่อมกับ input
- สถานะกำลังโหลดและข้อความผิดพลาดอ่านได้โดย screen reader
- ปุ่มปิดใช้งานเฉพาะรายการที่กำลังส่ง ไม่ล็อกทั้งหน้าโดยไม่จำเป็น

## 10. การจัดการข้อผิดพลาด

| รหัส | ความหมายใน flow นี้ | พฤติกรรมหน้าเว็บ |
| --- | --- | --- |
| 401 | session หมดอายุหรือไม่ได้เข้าสู่ระบบ | แจ้งให้เข้าสู่ระบบใหม่และพาไปหน้า login |
| 403 | บทบาทไม่ถูกต้องหรือเทรนเนอร์ยังไม่อนุมัติ | แสดงข้อความไม่มีสิทธิ์/สถานะอนุมัติ โดยไม่ลองส่งซ้ำอัตโนมัติ |
| 404 | ไม่พบ trainer, slot, booking หรือไฟล์ | แจ้งว่าไม่พบข้อมูลและกลับไปโหลดรายการล่าสุด |
| 409 | slot ถูกจองแล้ว, ช่วงเวลาทับซ้อน หรือคำขอถูกตอบไปแล้ว | คงข้อมูลที่ผู้ใช้กรอกไว้ แจ้งว่าข้อมูลเปลี่ยน และ refresh รายการที่เกี่ยวข้อง |
| 422 | รูปแบบหรือเงื่อนไขข้อมูลไม่ถูกต้อง | แสดงข้อความใกล้ field ที่ต้องแก้ |
| 500/เครือข่าย | API หรือ XAMPP ขัดข้อง | คงข้อมูลบนหน้า แสดงปุ่มลองใหม่ และห้ามแสดงผลสำเร็จปลอม |

API error ต้องมีข้อความภาษาไทยที่ใช้แสดงได้และ code ที่หน้าเว็บใช้แยกกรณี โดยไม่ส่ง stack trace หรือ path ภายในเครื่อง

## 11. ความปลอดภัยและความถูกต้องของข้อมูล

- ทุก endpoint ที่เปลี่ยนข้อมูลเรียก auth และตรวจ role ฝั่ง server
- การอ้าง id จาก request ต้องตรวจ ownership จากฐานข้อมูล ห้ามเชื่อข้อมูล role หรือ trainer id ที่ browser ส่งมา
- ไฟล์ใบรับรองเข้าถึงได้เฉพาะแอดมินผ่าน handler ที่ตรวจสิทธิ์
- ชื่อไฟล์/path จริงไม่ถูกส่งใน JSON สาธารณะ
- query ใช้ prepared statements
- transaction rollback เมื่อขั้นตอนใดขั้นตอนหนึ่งล้มเหลว
- การตรวจสถานะและการเปลี่ยนสถานะทำบนแถวที่ถูกล็อก เพื่อป้องกัน double action
- ห้ามใช้ข้อมูลสาธิตสร้าง booking หรือแสดงผลสำเร็จแทนผลจาก API

## 12. กลยุทธ์การทดสอบ

### 12.1 กฎฝั่ง PHP/API

ทดสอบอย่างน้อย:

- แอดมินอนุมัติใบสมัคร pending สำเร็จ และสถานะใบรับรองเปลี่ยนพร้อมกัน
- แอดมินปฏิเสธโดยไม่มี note ได้ `422`
- การตัดสินใบสมัครที่ไม่ใช่ pending ได้ `409`
- เทรนเนอร์ pending/rejected สร้าง slot ไม่ได้
- สร้าง slot ปกติได้
- slot ที่เริ่มในอดีต, สิ้นสุดก่อนเริ่ม, เกินสองเดือน หรือทับซ้อนถูกปฏิเสธ
- ลบได้เฉพาะ slot อนาคตที่ยัง available และเป็นของตน
- สมาชิกจอง slot ที่ว่างได้และ slot เปลี่ยนเป็น held
- การจอง slot เดียวกันพร้อมกันมีเพียงคำขอเดียวที่สำเร็จ อีกคำขอได้ `409`
- เทรนเนอร์อื่นตอบ booking ไม่ได้
- ตอบรับจาก pending_trainer ไป awaiting_payment ได้และ slot ยัง held
- ปฏิเสธจาก pending_trainer ไป cancelled ได้และ slot กลับ available
- การตอบ booking เดิมซ้ำได้ `409`

### 12.2 Flow ครบวงจร

ทดสอบด้วยบัญชีแยกตามบทบาท:

1. แอดมินเปิดใบรับรองและอนุมัติเทรนเนอร์
2. เทรนเนอร์สร้าง slot ในอนาคต
3. สมาชิกค้นหาเทรนเนอร์ เลือก slot และส่งคำขอ
4. เทรนเนอร์เห็นข้อมูลสมาชิกและตอบรับ
5. สมาชิกเห็นสถานะ `awaiting_payment`

ทดสอบเส้นทางปฏิเสธแยกต่างหากและยืนยันว่า slot เดิมกลับมาให้สมาชิกคนอื่นเลือกได้

### 12.3 คุณภาพหน้าเว็บ

- lint
- TypeScript typecheck
- production build
- ทดสอบใน browser ที่ขนาด desktop และ mobile
- ตรวจ loading, empty, success, validation, 401, 403, 409 และ API unavailable

## 13. เกณฑ์ยอมรับงาน

งานถือว่าเสร็จเมื่อ:

- แอดมินเปิดใบรับรองจริงและตัดสินใบสมัคร pending ได้
- เทรนเนอร์เห็นสถานะอนุมัติจริง; เฉพาะ approved trainer สร้างและลบ slot ตามกฎได้
- สมาชิกค้นหา trainer และ slot จากฐานข้อมูลจริงและส่ง booking ได้
- slot เดียวกันไม่สามารถสร้าง booking ที่ยังมีผลได้มากกว่าหนึ่งรายการจากการส่งพร้อมกัน
- เทรนเนอร์เห็นเฉพาะคำขอของตนและตอบรับหรือปฏิเสธได้ครั้งเดียว
- การปฏิเสธทำให้ booking เป็น cancelled และคืน slot เป็น available ทันที
- ประวัติสถานะ booking ถูกบันทึกทุกครั้ง
- หน้าเว็บไม่ใช้ข้อมูลสาธิตใน flow ที่เปลี่ยนข้อมูลจริง
- การทดสอบ API, lint, typecheck, build และ browser flow ผ่าน
- flow การชำระเงินและส่วนที่มีอยู่เดิมยังทำงานได้

## 14. ขอบเขตไฟล์ที่คาดว่าจะเปลี่ยน

- `backend/index.php` เพิ่ม route ของ trainer profile และ availability
- `backend/src/Handlers.php` เพิ่ม handler และทำ state/permission/transaction ให้รัดกุม
- helper ฝั่ง PHP สำหรับ validation/state rules และชุดทดสอบที่เกี่ยวข้อง
- `components/role-dashboard.tsx` เชื่อมคิวแอดมิน ตารางเทรนเนอร์ และคิว booking จริง
- `components/booking-form.tsx` เปลี่ยนจาก demo data เป็นข้อมูล trainer/slot จาก API
- `components/trainer-discovery.tsx` ปรับเฉพาะส่วนที่ต้องแบ่งปันการเลือก trainer/slot หรือ refresh ข้อมูล
- `lib/api.ts` และ `lib/types.ts` เพิ่ม contract ที่จำเป็น
- CSS/component ย่อยเฉพาะที่จำเป็นต่อสถานะและ responsive layout

การเปลี่ยนแปลงต้องรักษางาน header/auth ที่มีอยู่ใน working tree และไม่เขียนทับการแก้ไขที่ไม่เกี่ยวข้อง
