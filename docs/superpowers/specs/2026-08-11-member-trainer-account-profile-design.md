# FitConnect: โปรไฟล์บัญชีสมาชิกและเทรนเนอร์

วันที่อนุมัติแนวทาง: 11 สิงหาคม 2026
แนวทางที่อนุมัติ: หน้า `/profile` ร่วมกันและแสดงข้อมูลตามบทบาท

## 1. เป้าหมาย

- สร้างหน้าโปรไฟล์บัญชีสำหรับสมาชิกและเทรนเนอร์ โดยใช้ลำดับข้อมูลจากภาพอ้างอิง แต่คง Sidebar สี ตัวอักษร และภาษาภาพของ FitConnect
- ให้ผู้ใช้ดูและแก้ไขข้อมูลที่ระบบมีจริงได้จากหน้าเดียว
- เติมข้อมูลสมาชิกที่ระบุในบทที่ 3 แต่ยังไม่มีในฐานข้อมูลที่ติดตั้งจริง
- ให้สมาชิกและเทรนเนอร์เปลี่ยนรูปโปรไฟล์และรหัสผ่านได้
- คงข้อมูลและบัญชีเดิมไว้โดยไม่บังคับสร้างบัญชีใหม่

## 2. แหล่งข้อมูลและข้อสรุปที่ยืนยันแล้ว

พจนานุกรมข้อมูลหน้า 45 ของ `บทที่ 3.pdf` ระบุข้อมูลสมาชิก ได้แก่ รหัสสมาชิก ชื่อ นามสกุล อีเมล เบอร์โทร เป้าหมายการออกกำลังกาย ระดับประสบการณ์ น้ำหนัก และส่วนสูง

ภาพตัวอย่างหน้า 50 มีเพศและวันเกิดเพิ่มเติม แต่สองข้อมูลนี้ไม่อยู่ในพจนานุกรมข้อมูล ผู้ใช้ยืนยันว่าไม่ต้องเพิ่ม เพื่อลดความขัดแย้งในเอกสารให้ยึดพจนานุกรมข้อมูลเป็นหลัก

ฐานข้อมูลปัจจุบันแยกข้อมูลเข้าสู่ระบบไว้ใน `users` และข้อมูลสมาชิกไว้ใน `member_profiles` โครงสร้างใหม่นี้ต้องคงการแยกดังกล่าว ไม่สร้างตาราง `Members` ซ้ำอีกชุด

## 3. ขอบเขต

### อยู่ในขอบเขต

- หน้า `/profile` สำหรับบทบาท `member` และ `trainer`
- เมนู “โปรไฟล์” ใน Sidebar และคำสั่ง “ดูโปรไฟล์” ในเมนูบัญชี
- อ่านและแก้ไขข้อมูลส่วนตัวของสมาชิก
- อ่านและแก้ไขข้อมูลส่วนตัวและข้อมูลวิชาชีพของเทรนเนอร์
- อัปโหลดหรือเปลี่ยนรูปโปรไฟล์
- เปลี่ยนรหัสผ่านขณะเข้าสู่ระบบ
- API, validation และ migration ที่จำเป็นต่อข้อมูลข้างต้น
- Loading, error, validation, success, responsive และ accessibility states

### อยู่นอกขอบเขต

- เพศและวันเกิด
- จังหวัด พื้นที่ให้บริการ และสถานที่นัดฝึก
- ที่อยู่ สัญชาติ และข้อมูลอื่นจากภาพอ้างอิงที่ไม่มีในบทที่ 3
- บัญชีธนาคารหรือ QR Code รับเงิน
- อีเมลยืนยัน ลืมรหัสผ่านทางอีเมล และการเปลี่ยนอีเมล
- สถิติสุขภาพ ประวัติการออกกำลังกาย หรือระบบแนะนำเทรนเนอร์ใหม่
- หน้าโปรไฟล์ของแอดมิน
- การเปลี่ยนกติกาการจอง การชำระเงิน แชต รีวิว หรือการอนุมัติเทรนเนอร์

## 4. เส้นทางและการนำทาง

- สมาชิกและเทรนเนอร์ใช้เส้นทางเดียวคือ `/profile`
- หน้าอ่านบทบาทจากผู้ใช้ที่เข้าสู่ระบบและแสดงฟอร์มตามบทบาท ไม่รับบทบาทจาก query string
- ผู้ที่ยังไม่เข้าสู่ระบบถูกส่งไป `/login`
- แอดมินไม่ใช้หน้านี้และกลับไป `/admin`
- Sidebar ของสมาชิกและเทรนเนอร์เพิ่มรายการ “โปรไฟล์” พร้อมไอคอนบุคคล
- เมนูบัญชีด้านล่าง Sidebar เพิ่มลิงก์ “ดูโปรไฟล์” เหนือปุ่มออกจากระบบ
- `/profile` แสดงสถานะเมนูปัจจุบันทั้ง Desktop และ Mobile ตามรูปแบบ navigation เดิม

## 5. โครงหน้าและลำดับชั้น

หน้าใช้ Sidebar ของ FitConnect ที่มีอยู่แล้ว ไม่สร้าง Settings rail ซ้อนอีกชั้น

1. แถบหัวเนื้อหาแสดง breadcrumb “บัญชีของฉัน / โปรไฟล์”
2. ส่วนตัวตนแสดงรูป ชื่อ อีเมล ป้ายบทบาท และปุ่ม “เปลี่ยนรูป”
3. ส่วนข้อมูลใช้กรอบเส้นบางและแถวข้อมูลแบบเป็นระเบียบ ไม่แตกเป็นการ์ดย่อยจำนวนมาก
4. ส่วนข้อมูลส่วนตัวอยู่ก่อนข้อมูลเฉพาะบทบาท
5. ส่วนความปลอดภัยอยู่ท้ายหน้าและแยกการบันทึกจากข้อมูลโปรไฟล์

บน Desktop เนื้อหากว้างไม่เกินระบบ page shell เดิม ฟอร์มใช้สองคอลัมน์เมื่อช่องสัมพันธ์กัน บน Mobile เรียงหนึ่งคอลัมน์ ปุ่มบันทึกเต็มความกว้าง และไม่มี horizontal overflow

## 6. ข้อมูลสมาชิก

สมาชิกแก้ไขข้อมูลต่อไปนี้ได้:

- ชื่อ
- นามสกุล
- เบอร์โทรศัพท์
- เป้าหมายการออกกำลังกาย
- ระดับประสบการณ์
- น้ำหนักหน่วยกิโลกรัม
- ส่วนสูงหน่วยเซนติเมตร

อีเมลแสดงแบบอ่านอย่างเดียว รหัสสมาชิกไม่ต้องแสดงเป็นช่องแก้ไข `medical_note` เดิมต้องไม่ถูกลบหรือเขียนทับ แต่ยังไม่เปิดให้แก้ในหน้านี้เพราะไม่อยู่ในชุดข้อมูลที่ผู้ใช้อนุมัติ

ค่า `display_name` ที่ระบบอื่นใช้อยู่ต้องอัปเดตจากชื่อและนามสกุลหลังบันทึก เพื่อให้ Sidebar แชต และหน้าการจองใช้ชื่อใหม่ทันที

## 7. ข้อมูลเทรนเนอร์

เทรนเนอร์แก้ไขข้อมูลต่อไปนี้ได้:

- ชื่อที่แสดง
- ชื่อจริง
- เบอร์โทรศัพท์
- หัวข้อแนะนำตัว
- ประวัติส่วนตัว
- จำนวนปีประสบการณ์
- รูปแบบการให้บริการ ได้แก่ฟรีแลนซ์ ประจำยิม หรือทั้งสองแบบ
- ชื่อยิม เมื่อรูปแบบการให้บริการเกี่ยวข้องกับยิม
- ค่าฝึกต่อครั้ง
- ประเภทการฝึกหรือความเชี่ยวชาญจากรายการประเภทที่ระบบมีอยู่

อีเมลแสดงแบบอ่านอย่างเดียว สถานะการอนุมัติ เหตุผลจากแอดมิน และใบรับรองแสดงแบบอ่านอย่างเดียว การแก้ข้อมูลโปรไฟล์ไม่เปลี่ยนสถานะอนุมัติอัตโนมัติและไม่สร้างขั้นตอนอนุมัติใหม่

## 8. รูปโปรไฟล์

- สมาชิกและเทรนเนอร์อัปโหลด JPG, PNG หรือ WebP ได้
- ขนาดสูงสุด 5 MB ตามข้อจำกัดอัปโหลดของระบบปัจจุบัน
- ตรวจทั้งนามสกุล MIME type และความสำเร็จของการอ่านรูป
- ตั้งชื่อไฟล์ใหม่ฝั่งเซิร์ฟเวอร์และเก็บเฉพาะ path ที่ปลอดภัย ห้ามใช้ชื่อไฟล์จากผู้ใช้เป็น path โดยตรง
- การอัปโหลดสำเร็จต้องอัปเดตรูปในหัวหน้าและ Sidebar ทันที
- การอัปโหลดไม่สำเร็จต้องคงรูปเดิม
- สมาชิกที่ยังไม่มีรูปใช้ตัวอักษรย่อจากชื่อ เทรนเนอร์ที่ยังไม่มีรูปใช้ fallback เดิมของระบบ
- การแทนที่รูปเดิมลบไฟล์เก่าหลังฐานข้อมูลบันทึกไฟล์ใหม่สำเร็จเท่านั้น

## 9. ความปลอดภัยและรหัสผ่าน

ฟอร์มเปลี่ยนรหัสผ่านมีช่องรหัสผ่านปัจจุบัน รหัสผ่านใหม่ และยืนยันรหัสผ่านใหม่

- ต้องตรวจรหัสผ่านปัจจุบันฝั่งเซิร์ฟเวอร์
- รหัสผ่านใหม่ยาวอย่างน้อย 8 ตัวอักษรตามกติกาสมัครสมาชิกเดิม
- รหัสผ่านใหม่และยืนยันรหัสผ่านต้องตรงกัน
- ห้ามส่งคืน password hash ใน API หรือ log
- เมื่อเปลี่ยนสำเร็จให้คงเซสชันปัจจุบันและยกเลิก token อื่นของบัญชี
- แสดงข้อความสำเร็จโดยไม่แสดงค่ารหัสผ่าน และล้างช่องรหัสผ่านทั้งหมด

## 10. API และโครงสร้างข้อมูล

ใช้ endpoint ที่สั้นและตรงหน้าที่:

- `GET /v1/profile` อ่านข้อมูลโปรไฟล์ตามบทบาท
- `PATCH /v1/profile` แก้ข้อมูลโปรไฟล์ตามบทบาท
- `POST /v1/profile/image` อัปโหลดหรือเปลี่ยนรูป
- `PATCH /v1/profile/password` เปลี่ยนรหัสผ่าน

ทุก endpoint ต้องใช้ bearer token และอ้างอิง user id จาก token เท่านั้น ห้ามรับ user id เป้าหมายจาก client

เพิ่มข้อมูลใน `member_profiles` โดย migration แบบรักษาข้อมูลเดิม:

- `first_name VARCHAR(100) NULL`
- `last_name VARCHAR(100) NULL`
- `experience_level VARCHAR(50) NULL`
- `weight DECIMAL(5,2) NULL`
- `height DECIMAL(5,2) NULL`
- `image_path VARCHAR(500) NULL`

คง `phone`, `goals`, `medical_note`, timestamps และ foreign key เดิม บัญชีเดิมให้ใช้ `users.display_name` เป็นชื่อเริ่มต้นเมื่อ `first_name` ยังว่าง และไม่พยายามแยกชื่อไทยอัตโนมัติ

ตาราง `trainer_profiles` ใช้คอลัมน์เดิม รวมถึง `legal_name`, `phone`, `headline`, `bio`, `years_experience`, `service_mode`, `gym_name`, `price_from` และ `image_path` ไม่สร้างตารางโปรไฟล์เทรนเนอร์ใหม่

## 11. Validation และสถานะหน้าจอ

- ชื่อและนามสกุลสมาชิกต้องไม่ว่างเมื่อบันทึก
- ชื่อที่แสดงของเทรนเนอร์ต้องไม่ว่าง
- เบอร์โทรเป็นข้อมูลเลือกกรอก แต่ต้องตรวจรูปแบบและความยาวเมื่อมีค่า
- น้ำหนักและส่วนสูงเป็นค่าบวกและอยู่ในช่วงที่ฐานข้อมูลรองรับ
- ปีประสบการณ์เป็นจำนวนเต็มตั้งแต่ศูนย์
- ราคาเป็นค่าบวกเมื่อมีค่า
- ชื่อยิมแสดงและตรวจเฉพาะรูปแบบประจำยิมหรือทั้งสองแบบ
- ข้อผิดพลาดรายช่องผูกกับ input ที่เกี่ยวข้อง
- ระหว่างบันทึกปิดปุ่มซ้ำและแสดงข้อความกำลังบันทึก
- บันทึกสำเร็จแสดงข้อความสถานะที่โปรแกรมอ่านหน้าจอรับรู้ได้
- โหลดไม่สำเร็จแสดง `role="alert"` และปุ่ม “ลองใหม่” โดยไม่แสดงฟอร์มว่างปลอม
- ไม่มีการบันทึกอัตโนมัติ

## 12. รูปลักษณ์และข้อความ

- ใช้ deep forest, lime accent, เส้นขอบ และ typography tokens เดิมของ FitConnect
- ไม่ใช้ gradient, glass effect, เงาหนัก หรือการ์ดซ้อนหลายชั้น
- รูปโปรไฟล์เป็นวงกลมขนาดกะทัดรัด ไม่แย่งน้ำหนักจากชื่อและข้อมูล
- หัวข้อใช้ภาษาไทยสั้นและตรง เช่น “ข้อมูลส่วนตัว”, “ข้อมูลการออกกำลังกาย”, “ข้อมูลวิชาชีพ”, “ความปลอดภัย”
- ใช้ข้อความจริงของระบบ ไม่ใส่คำว่า “ข้อมูลสาธิต” หรือคำอธิบายเชิงต้นแบบ
- ป้ายอนุมัติของเทรนเนอร์ต้องใช้คำสถานะที่ระบบมีจริงและไม่กล่าวอ้างว่าใบรับรองได้รับการรับรองโดยหน่วยงานภายนอก

## 13. Accessibility และ Responsive

- ทุก input มี label ที่มองเห็นได้
- ช่องอ่านอย่างเดียวมีคำอธิบายว่าเหตุใดจึงแก้ไม่ได้
- ปุ่มอัปโหลดมีชื่อที่ชัดและแสดงชื่อไฟล์หรือรูปตัวอย่างโดยไม่พึ่งสี
- focus ring ชัดเจนและลำดับ Tab เดินตามลำดับเนื้อหา
- ข้อความผิดพลาดเชื่อมด้วย `aria-describedby`
- สถานะสำเร็จและกำลังบันทึกใช้ live region ที่เหมาะสม
- รองรับ 1280, 768, 414, 375 และ 320px รวมถึง 200% zoom
- ปุ่มและช่องควบคุมสูงอย่างน้อย 44px
- reduced motion ปิดการเคลื่อนไหวที่ไม่จำเป็น

## 14. การทดสอบ

การทดสอบฝั่งหน้าเว็บต้องครอบคลุม:

- บทบาทสมาชิกและเทรนเนอร์เห็นส่วนข้อมูลที่ถูกต้องและไม่เห็นข้อมูลของอีกบทบาท
- อีเมลเป็น read-only
- ค่าเดิมถูกเติมครบ รวมทั้ง fallback ของบัญชีสมาชิกเดิม
- validation รายช่องและการป้องกัน submit ซ้ำ
- บันทึกสำเร็จอัปเดตชื่อและรูปใน UI
- loading, error, retry และ success states
- อัปโหลดรูปชนิดถูกต้อง ชนิดผิด และขนาดเกิน 5 MB
- เปลี่ยนรหัสผ่านสำเร็จ รหัสเดิมผิด และยืนยันรหัสไม่ตรง
- เมนู Sidebar และเมนูบัญชีไป `/profile` ถูกต้อง

การทดสอบ PHP/API ต้องครอบคลุม:

- auth และ role guard ของทุก endpoint
- อ่านและบันทึกสมาชิกโดยไม่เขียนทับ `medical_note`
- อ่านและบันทึกเทรนเนอร์โดยไม่เปลี่ยนสถานะอนุมัติ
- validation และ transaction rollback
- upload validation, path safety และการคงรูปเดิมเมื่อเกิดข้อผิดพลาด
- password verification, password hash ใหม่ และการยกเลิก token อื่น
- migration ทำงานได้ทั้งฐานข้อมูลใหม่และฐานข้อมูลเดิม
