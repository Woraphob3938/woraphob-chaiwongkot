# FitConnect: เมนูตามบทบาท การเริ่มต้นใช้งานเทรนเนอร์ และการนำจังหวัดออก

วันที่: 10 สิงหาคม 2026

สถานะ: ข้อตกลงการออกแบบได้รับการยืนยันแล้ว และรอตรวจทานสเปกฉบับเขียน

## 1. เป้าหมาย

ปรับ FitConnect ให้แต่ละบทบาทเห็นงานที่เกี่ยวข้องกับตนเอง ลดความรู้สึกว่าผู้ใช้ต้องสมัครเป็นเทรนเนอร์ซ้ำ และนำข้อมูลจังหวัดกับสถานที่นัดฝึกออกจากระบบทั้งหมด โดยยังคงขั้นตอนหลักหลังการจองไว้เหมือนเดิม

ผลลัพธ์ที่ต้องได้:

1. เฉพาะสมาชิกเห็นเมนู “ค้นหาเทรนเนอร์” และ “การจองของฉัน” ทั้งบนเดสก์ท็อปและมือถือ
2. ผู้สมัครเทรนเนอร์ทำขั้นตอนบัญชีและข้อมูลวิชาชีพเป็นกระบวนการต่อเนื่องสองขั้นตอน
3. ผู้สมัครที่หยุดกลางทางกลับมาทำขั้นตอนข้อมูลวิชาชีพต่อได้หลังเข้าสู่ระบบ
4. จังหวัด พื้นที่ให้บริการ และสถานที่นัดฝึกไม่ปรากฏใน UI, API, type, ข้อมูลสาธิต หรือฐานข้อมูล
5. ตารางว่าง การจอง การชำระเงิน แชต รีวิว และการอนุมัติเทรนเนอร์ยังทำงานต่อเนื่องกับข้อมูลจริง

ระบบยังใช้ Next.js, PHP API ภายใต้ XAMPP และ MySQL ตามสถาปัตยกรรมปัจจุบัน

## 2. สิ่งที่อยู่นอกขอบเขต

- เปลี่ยนบทบาทหรือสิทธิ์ของแอดมิน
- เปลี่ยนกฎตารางว่างและสถานะการจอง
- เปลี่ยนกฎการแจ้งราคา การอัปโหลดสลิป การตรวจชำระเงิน แชต หรือรีวิว
- เปลี่ยนประเภทการฝึก รูปแบบการทำงาน ชื่อฟิตเนส หรือราคาเริ่มต้น
- เพิ่มแผนที่ พิกัด GPS ที่อยู่ หรือระบบค้นหาตามระยะทางเพื่อทดแทนจังหวัด
- ทำให้หน้าและ API รายชื่อเทรนเนอร์เป็นข้อมูลลับ งานนี้เปลี่ยนการนำทางตามบทบาท ไม่เปลี่ยนสัญญาการอ่านข้อมูลสาธารณะที่มีอยู่

## 3. สภาพระบบปัจจุบัน

- `SiteHeader` ใช้รายการเมนูร่วมกันทุกบทบาท จึงแสดงงานของสมาชิกให้เทรนเนอร์และแอดมินเห็น
- Register ให้เลือกบทบาทเทรนเนอร์ แต่ API สมัครบัญชีสร้างเพียงแถว `users`; ข้อมูลโปรไฟล์และใบรับรองถูกเก็บผ่านใบสมัครอีกหน้าหลังเข้าสู่ระบบ
- บัญชีเทรนเนอร์ที่ยังไม่มี `trainer_profiles` จึงรู้สึกเหมือนต้อง “สมัครเป็นเทรนเนอร์” เป็นครั้งที่สอง
- จังหวัดผูกกับรายการเทรนเนอร์ แบบสมัคร ตัวกรอง DTO ข้อมูลสาธิต และหลาย foreign key ใน MySQL
- `bookings.location_text` เป็นข้อมูลบังคับจากฟอร์มจองและถูกแสดงซ้ำในหน้าสมาชิก เทรนเนอร์ แอดมิน และแชต

## 4. การนำทางตามบทบาท

ใช้แหล่งกำหนดเมนูตามบทบาทชุดเดียวสำหรับ desktop header และ mobile navigation เพื่อไม่ให้สองตำแหน่งแสดงสิทธิ์ต่างกัน

| สถานะผู้ใช้ | เมนูหลัก |
| --- | --- |
| ยังไม่เข้าสู่ระบบ | หน้าแรก สมัครบัญชี เข้าสู่ระบบ |
| สมาชิก | ค้นหาเทรนเนอร์, การจองของฉัน และทางเข้าพื้นที่สมาชิก |
| เทรนเนอร์ | พื้นที่เทรนเนอร์ ตารางว่าง คำขอจอง แชต และโปรไฟล์ของตน |
| แอดมิน | พื้นที่แอดมิน คิวตรวจเทรนเนอร์ และคิวตรวจการชำระเงิน |

ข้อกำหนดเพิ่มเติม:

- ปุ่มค้นหาใน header และข้อความ “ค้นหาเทรนเนอร์” แสดงในเมนูหลักเฉพาะสมาชิก
- “การจองของฉัน” หมายถึงรายการจองฝั่งสมาชิกเท่านั้น ไม่ใช้เป็นชื่อเมนูของเทรนเนอร์หรือแอดมิน
- เทรนเนอร์และแอดมินยังเข้าพื้นที่ของตนผ่านเมนูบทบาทและเมนูโปรไฟล์ได้
- การเปลี่ยน local session, login หรือ logout ต้องอัปเดตทั้ง desktop และ mobile โดยไม่ต้อง reload หน้า

## 5. การสมัครเทรนเนอร์สองขั้นตอน

### 5.1 ขั้นที่ 1: บัญชี

หน้า Register เก็บ:

- ชื่อที่ใช้ในระบบ
- อีเมล
- รหัสผ่าน
- บทบาทสมาชิกหรือเทรนเนอร์

สมาชิกที่สมัครสำเร็จเข้าสู่พื้นที่สมาชิกตามพฤติกรรมเดิม

เทรนเนอร์ที่สมัครสำเร็จจะได้รับ token ตามเดิม แต่ถูกพาเข้าสู่ขั้นที่ 2 ทันที หน้าเว็บใช้ข้อความ “ตั้งค่าโปรไฟล์เทรนเนอร์” ไม่ใช้ “สมัครเป็นเทรนเนอร์” ซ้ำ

### 5.2 ขั้นที่ 2: ข้อมูลวิชาชีพ

เก็บเฉพาะ:

- ชื่อ-นามสกุลตามเอกสาร
- เบอร์โทรศัพท์
- รูปแบบการทำงาน: ฟรีแลนซ์ ประจำฟิตเนส หรือทั้งสองแบบ
- ความเชี่ยวชาญหลัก
- ประสบการณ์และแนวทางการฝึก
- ใบรับรอง PDF ตามขนาดและชนิดไฟล์เดิม

ไม่มีจังหวัด พื้นที่ให้บริการ หรือสถานที่นัดฝึกในขั้นตอนนี้

เมื่อส่งสำเร็จ ระบบสร้างหรืออัปเดต `trainer_profiles`, ผูกประเภทการฝึกและใบรับรอง แล้วกำหนดสถานะ `pending` เพื่อให้แอดมินตรวจ

### 5.3 การกลับมาทำต่อ

หลัง Register หรือ Login ของบทบาทเทรนเนอร์ หน้าเว็บเรียก `GET /v1/trainer/me`:

- `profile = null` → เปิดขั้นที่ 2
- `pending` → เปิดพื้นที่เทรนเนอร์และแสดงว่ารอตรวจ
- `approved` → เปิดพื้นที่เทรนเนอร์ปกติ
- `rejected` → เปิดพื้นที่เทรนเนอร์ แสดงเหตุผล และให้แก้ข้อมูลส่งใหม่

ถ้าตรวจสถานะไม่สำเร็จ ให้แสดงข้อผิดพลาดกับปุ่มลองใหม่ ห้ามเดาว่าไม่มีโปรไฟล์หรือพาผู้ใช้ไปผิดขั้นตอน

หากขั้นที่ 2 ส่งไม่สำเร็จ บัญชียังคงใช้ได้ ข้อมูลที่กรอกในหน้าไม่ถูกล้าง และการลองใหม่ต้องไม่สร้างบัญชีซ้ำ

## 6. การนำจังหวัดและสถานที่นัดฝึกออกจาก UI

### 6.1 การค้นหาและโปรไฟล์เทรนเนอร์

- ลบตัวกรองจังหวัด query parameter จังหวัด และข้อความ “ทุกจังหวัด”
- ลบจังหวัดและพื้นที่ให้บริการออกจากการ์ด รายการ รายละเอียด และ accessible label
- การค้นหาเหลือชื่อเทรนเนอร์ ข้อความแนะนำตัว และความเชี่ยวชาญ
- ข้อมูลประกอบยังใช้รูปแบบการฝึก ชื่อฟิตเนส ราคา การตรวจคุณสมบัติ รีวิว และตารางว่าง
- ปรับ empty state และข้อความค้นหาไม่ให้แนะนำให้เปลี่ยนจังหวัดหรือพื้นที่

### 6.2 การจองและงานหลังการจอง

- ฟอร์มจองไม่รับสถานที่นัดฝึก
- request สร้างการจองส่งเฉพาะ `trainerId`, `slotId` และ `note`
- DTO และหน้าสมาชิก เทรนเนอร์ แอดมิน แชต และหลักฐานธุรกรรมไม่แสดง `location`
- ประวัติการจองเดิมยังคงวันเริ่ม วันสิ้นสุด เทรนเนอร์ สมาชิก ราคา สถานะ การชำระเงิน และข้อความ

## 7. การเปลี่ยน API contract

### 7.1 ยกเลิกจังหวัด

- ลบ `GET /v1/provinces`
- `GET /v1/trainers` และ `GET /v1/trainers/{slug}` ไม่ส่ง `province`, `region` หรือ `serviceAreas`
- `POST /v1/trainer-applications` ไม่รับและไม่ตรวจ `provinceId`
- รายการตรวจของแอดมินไม่ส่ง `province`

### 7.2 สร้างการจอง

`POST /v1/bookings`

request body ใหม่:

```json
{
  "trainerId": 12,
  "slotId": 353,
  "note": "ต้องการเน้นท่าพื้นฐาน"
}
```

`note` ยังคงเป็นทางเลือก กฎสิทธิ์ การล็อก slot, transaction, status history และการสร้างห้องแชตไม่เปลี่ยน

ผลลัพธ์จาก booking, payment review, chat facts และ admin queue จะไม่มี `location`

## 8. การเปลี่ยนฐานข้อมูล

ใช้ migration แบบระบุขั้นตอนชัดเจนและสำรองฐานข้อมูล XAMPP ก่อนดำเนินการจริง ห้ามแก้เฉพาะ schema ตั้งต้นโดยปล่อยฐานข้อมูลปัจจุบันไม่ตรงกัน

นำรายการต่อไปนี้ออก:

- ตาราง `trainer_service_areas`
- foreign key และคอลัมน์ `member_profiles.home_province_id`
- foreign key, index และคอลัมน์ `gyms.province_id`
- foreign key, index และคอลัมน์ `trainer_profiles.primary_province_id`
- คอลัมน์ `bookings.location_text`
- ตาราง `provinces` หลังไม่มี foreign key อ้างถึงแล้ว

ปรับ `schema.sql` และ `seed.sql` ให้ติดตั้งฐานข้อมูลใหม่ได้โดยไม่มีข้อมูลจังหวัดหรือสถานที่นัดฝึก ข้อมูลเทรนเนอร์สาธิตยังเก็บชื่อ ความเชี่ยวชาญ รูปแบบการฝึก ราคา ใบรับรอง และตารางว่าง

ชื่อฟิตเนส (`gym_name`) และข้อมูลฟิตเนสที่ไม่ใช่จังหวัดยังคงอยู่ เพราะไม่ใช่สถานที่เฉพาะของนัดหมาย

## 9. ความถูกต้องและการจัดการข้อผิดพลาด

- PHP API เป็นแหล่งความจริงของ role และสถานะอนุมัติ; การซ่อนเมนูไม่ใช้แทนการตรวจสิทธิ์ API
- การสร้างหรือแก้ใบสมัครกับข้อมูลประเภทการฝึกและใบรับรองใช้ transaction ตามขอบเขตที่ฐานข้อมูลรองรับ
- ถ้าบันทึกไฟล์สำเร็จแต่ transaction ล้มเหลว ต้องลบไฟล์กำพร้าตามกลไก upload เดิม
- การส่งใบสมัครซ้ำขณะคำขอกำลังทำงานต้องถูกป้องกัน
- ใบสมัครที่ `pending` ห้ามสร้างรายการ pending ซ้ำโดยไม่ตั้งใจ
- ใบสมัครที่ `rejected` แก้แล้วส่งใหม่ได้ และเปลี่ยนกลับเป็น `pending`
- Migration ต้องหยุดพร้อมข้อความชัดเจนหากโครงสร้างฐานข้อมูลไม่ตรงกับที่คาด ห้ามลบตารางแบบเดาสุ่ม

## 10. การทดสอบ

### 10.1 Frontend

- เมนู guest, member, trainer และ admin ทั้ง desktop/mobile
- การเปลี่ยน session และ logout ทำให้เมนูเปลี่ยนถูกต้อง
- Register สมาชิกยังไป `/member`
- Register เทรนเนอร์ไปขั้นที่ 2
- Login เทรนเนอร์ที่ยังไม่มีโปรไฟล์กลับมาขั้นที่ 2
- สถานะ pending, approved และ rejected ไปพื้นที่เทรนเนอร์และแสดงข้อความถูกต้อง
- ความล้มเหลวในการตรวจสถานะมี retry และไม่แสดงสถานะปลอม
- หน้า search, profile, booking, dashboard, admin และ chat ไม่มีจังหวัดหรือสถานที่นัดฝึก
- request การจองไม่มี `location`

### 10.2 PHP และฐานข้อมูล

- Register และ login ทุกบทบาทตามกฎเดิม
- ส่งใบสมัครโดยไม่มี `provinceId`
- ส่งใหม่หลัง rejected และป้องกันข้อมูลซ้ำ
- สร้าง booking โดยไม่มี `location`
- migration ทำงานกับสำเนาฐานข้อมูลปัจจุบันและติดตั้งใหม่จาก schema/seed ได้
- ตรวจว่าไม่มีตาราง คอลัมน์ foreign key หรือ seed จังหวัดหลงเหลือใน phpMyAdmin

### 10.3 ขั้นตอนครบวงจร

ทดสอบ Register เทรนเนอร์ → ตั้งค่าโปรไฟล์ → แอดมินอนุมัติ → สร้างตารางว่าง → สมาชิกค้นหาและจองโดยไม่มีสถานที่ → เทรนเนอร์ตอบรับ → สมาชิกอัปโหลดสลิป → แอดมินตรวจ → แชต → รีวิว

ตรวจผลด้วย frontend tests, PHP tests, lint, typecheck, production build และ live XAMPP smoke/audit

## 11. เกณฑ์ยอมรับงาน

- เทรนเนอร์และแอดมินไม่เห็น “ค้นหาเทรนเนอร์” หรือ “การจองของฉัน” ในเมนูใด ๆ
- เทรนเนอร์ไม่ต้องกด “สมัครเป็นเทรนเนอร์” หลังเลือกบทบาทนี้ใน Register
- ผู้สมัครเทรนเนอร์ที่ข้อมูลวิชาชีพยังไม่ครบกลับมาทำต่อหลัง Login ได้
- ไม่มีจังหวัด พื้นที่ให้บริการ หรือสถานที่นัดฝึกใน UI, request/response, type, demo data, schema, seed และฐานข้อมูลที่ migrate แล้ว
- ขั้นตอนอนุมัติ ตารางว่าง การจอง การชำระเงิน แชต และรีวิวผ่านการทดสอบครบวงจร
- ไม่เพิ่มงานนอกขอบเขต เช่น แผนที่ พิกัด หรือระบบสถานที่ทดแทน
