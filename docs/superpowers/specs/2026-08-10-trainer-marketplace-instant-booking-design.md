# FitConnect: หน้าค้นหาแบบ Marketplace และการจองรอชำระ 10 นาที

วันที่: 10 สิงหาคม 2026

สถานะ: ข้อตกลงการออกแบบได้รับการยืนยันแล้ว และรอตรวจทานสเปกฉบับเขียน

## 1. เป้าหมาย

ปรับเส้นทางของสมาชิกตั้งแต่ค้นหาเทรนเนอร์จนถึงยืนยันการจองให้เปรียบเทียบง่าย อ่านหลักฐานได้เร็ว และจองช่วงเวลาว่างได้ทันทีโดยไม่ต้องรอเทรนเนอร์กดรับ สมาชิกต้องอัปโหลดสลิปภายใน 10 นาทีเพื่อรักษาสิทธิ์ในช่วงเวลาที่เลือก หากไม่ส่งทัน ระบบคืนช่วงเวลาให้สมาชิกคนอื่นโดยอัตโนมัติเมื่อมีการใช้งาน API ครั้งถัดไป

ผลลัพธ์ที่ต้องได้:

1. หน้าค้นหาใช้โครง Marketplace Grid มีตัวกรองด้านซ้ายและการ์ดเทรนเนอร์แบบกริด
2. หน้าโปรไฟล์ใช้โครง Commerce Detail มีข้อมูลเทรนเนอร์ตรงกลางและแผงจองติดด้านขวาบนเดสก์ท็อป
3. ราคาบนโปรไฟล์เป็นค่าฝึกต่อครั้งที่ใช้ชำระจริง ไม่ใช่ราคาเริ่มต้นที่รอเทรนเนอร์ยืนยัน
4. การจองใหม่เข้าสู่ขั้นรอชำระทันทีและล็อกช่วงเวลาไว้ 10 นาที
5. เทรนเนอร์ไม่ต้องรับ ปฏิเสธ หรือกรอกราคาสำหรับการจอง
6. การปฏิเสธสลิปครั้งแรกให้เวลาส่งใหม่ 10 นาทีหนึ่งครั้ง การปฏิเสธครั้งที่สองทำให้การจองหมดอายุ
7. ทุกสถานะ ราคา เส้นตาย สลิป และการคืนช่วงเวลาถูกบันทึกและตรวจได้ใน phpMyAdmin

โปรเจกต์ใช้ Next.js 16.3.0, React, TypeScript, shadcn, PHP API ภายใต้ XAMPP และ MySQL/MariaDB ตามสถาปัตยกรรมปัจจุบัน

## 2. ขอบเขต

### 2.1 อยู่ในขอบเขต

- หน้าค้นหา `/trainers`
- หน้าโปรไฟล์ `/trainers/[id]`
- หน้ายืนยันการจอง `/booking`
- แถบสรุปการจองและหน้าสมาชิก
- พื้นที่เทรนเนอร์ส่วนตารางและรายการนัด
- คิวตรวจสลิปของแอดมิน
- API สร้างการจอง อัปโหลดสลิป ตรวจสลิป และอ่านข้อมูลที่เกี่ยวข้อง
- สถานะการจอง ประวัติสถานะ และการคืน availability slot
- การ migration ฐานข้อมูล XAMPP ปัจจุบันและ schema สำหรับติดตั้งใหม่

### 2.2 อยู่นอกขอบเขต

- ระบบรับชำระเงินจริงผ่านธนาคารหรือ payment gateway
- การตรวจสลิปอัตโนมัติ
- แพ็กเกจหลายราคา คูปอง ส่วนลด หรือระบบตะกร้า
- ราคาที่แตกต่างกันในแต่ละช่วงเวลา
- จังหวัด พื้นที่ให้บริการ สถานที่นัดฝึก แผนที่ หรือพิกัด
- ระบบแนะนำเทรนเนอร์ด้วย AI หรือคะแนนจัดอันดับที่สร้างขึ้นใหม่
- การเปลี่ยนกฎการอนุมัติเทรนเนอร์ แชต การปิดงาน และรีวิวที่ไม่เกี่ยวกับขั้นรอชำระ

## 3. แนวทางภาพและโครงหน้าจอ

ภาพอ้างอิงจาก Advice ใช้เฉพาะแนวทางด้านลำดับข้อมูล ได้แก่ตัวกรอง รายการแบบกริด หน้ารายละเอียด และแผงทำรายการด้านข้าง FitConnect ไม่คัดลอกสีน้ำเงิน โลโก้ เมนู ข้อความ รูปทรง หรือรายละเอียดการขายสินค้า

ระบบภาพยังใช้ Athlete Credential ตาม `DESIGN.md`:

- สีเขียวเข้มเป็นหมึกและโครงสร้างหลัก
- สีเขียวมะนาวใช้กับการเลือก focus และ primary action
- พื้นผิวเป็นสีทึบ เส้นแบ่งชัด และรัศมีมุมขนาดเล็ก
- Chakra Petch ใช้กับหัวข้อ Bai Jamjuree ใช้กับข้อความไทย และ JetBrains Mono ใช้กับราคา เวลา และรหัส
- แสดงข้อมูลสาธิตและภาพสังเคราะห์ด้วยป้ายกำกับที่มองเห็นได้
- ไม่มีคะแนน รีวิว จำนวนผู้ใช้ หรือหลักฐานที่ไม่มีข้อมูลจริงรองรับ

ใช้ shadcn เฉพาะส่วนที่ช่วยพฤติกรรมและ accessibility ได้แก่ `Button`, `Input`, `Badge`, `Sheet`, `Dialog`, `NativeSelect` และ primitive ที่มีอยู่แล้ว ไม่เพิ่มไลบรารี UI ชุดใหม่

## 4. หน้าค้นหาเทรนเนอร์

### 4.1 ลำดับข้อมูล

1. ชื่อหน้าและคำอธิบายสั้น
2. ช่องค้นหาชื่อหรือความเชี่ยวชาญ
3. ตัวกรอง
4. จำนวนผลลัพธ์และตัวเลือกเรียงลำดับ
5. การ์ดเทรนเนอร์แบบกริด
6. empty, loading และ error state พร้อมคำสั่งที่เกี่ยวข้อง

### 4.2 ตัวกรอง

ตัวกรองใช้ข้อมูลที่ระบบมีอยู่หรือคำนวณจากข้อมูลจริงเท่านั้น:

- ประเภทการฝึก
- ช่วงราคา
- ผ่านการตรวจคุณสมบัติ
- มีช่วงเวลาว่าง

การเรียงลำดับรองรับเวลาว่างใกล้สุดและราคา ไม่เพิ่มระบบจัดอันดับลับหรือคะแนนแนะนำ

### 4.3 การ์ดเทรนเนอร์

การ์ดหนึ่งใบแสดง:

- รูปและป้ายข้อมูลสาธิตเมื่อเกี่ยวข้อง
- ชื่อและความเชี่ยวชาญหลัก
- สถานะตรวจคุณสมบัติ
- ประสบการณ์
- ราคาต่อครั้ง
- ช่วงเวลาว่างใกล้สุดเมื่อมี
- รีวิวและคะแนนเฉพาะเมื่อ API มีรีวิวจริง
- primary action เดียว: “ดูโปรไฟล์และเลือกเวลา”

การคลิกการ์ดหรือปุ่มไปหน้าโปรไฟล์ ไม่เลือก slot หรือสร้างการจองจากหน้ารายการ

### 4.4 Responsive

- 1280px: ตัวกรองซ้ายและกริดสามคอลัมน์
- 768px: ตัวกรองเปิดผ่าน `Sheet` และกริดสองคอลัมน์
- 414, 375 และ 320px: กริดหนึ่งคอลัมน์ ตัวกรองอยู่ใน `Sheet`
- ไม่มีรางการ์ดแนวนอนและไม่มี page-level horizontal overflow
- ชื่อ ราคา เวลา และปุ่มต้องอ่านได้ที่ 200% zoom

## 5. หน้าโปรไฟล์และแผงจอง

### 5.1 เดสก์ท็อป

ใช้สามโซนตามลำดับ DOM เดียวกับการอ่าน:

1. รูปโปรไฟล์และหลักฐานภาพ
2. ชื่อ สถานะตรวจ ความเชี่ยวชาญ ประสบการณ์ ราคา ประวัติ ใบรับรอง และรีวิวจริง
3. แผงเลือกวัน เวลา ราคา และปุ่ม “จองเวลานี้”

แผงจองติดหน้าจอเมื่อเลื่อน แต่ต้องไม่ทับ header, footer หรือเนื้อหา ราคาที่แสดงเป็นราคาต่อครั้งเดียวกับยอดที่จะบันทึกตอนจอง

ข้อมูลรอง เช่นใบรับรองทั้งหมด ตารางว่างทั้งหมด และรีวิวเพิ่มเติมใช้ native disclosure ที่มีชื่อชัดเจน เนื้อหาที่จำเป็นต่อการยืนยันการจองไม่ถูกซ่อนไว้

### 5.2 มือถือและแท็บเล็ต

- เรียงรูปและตัวตนก่อน ตามด้วยข้อมูลสำคัญและตัวเลือกเวลา
- แถบด้านล่างแสดงชื่อเทรนเนอร์ วัน เวลา ราคา และปุ่มจองเมื่อเลือกข้อมูลครบ
- sticky control ไม่ทับฟอร์ม ข้อผิดพลาด หรือ footer
- ทุก touch target สูงอย่างน้อย 44px

### 5.3 Dialog ยืนยัน

ก่อนสร้างการจอง Dialog แสดงข้อมูลที่เปลี่ยนสิทธิ์ของ slot ครบ:

- เทรนเนอร์
- วันและเวลา
- ราคาต่อครั้ง
- ข้อความว่า slot จะถูกเก็บไว้ 10 นาที
- ข้อความว่าต้องอัปโหลดสลิปก่อนหมดเวลา

ปุ่มหลักใช้ “ยืนยันและเริ่มเวลา 10 นาที” ปุ่มรองใช้ “กลับไปเลือกเวลา”

## 6. กฎราคา

- `trainer_profiles.price_from` เปลี่ยนความหมายใน UI และ contract เป็นราคาต่อครั้ง
- เทรนเนอร์ต้องมีราคาที่มากกว่า 0 ก่อนโปรไฟล์พร้อมรับการจอง
- เมื่อสร้างการจอง API คัดลอกราคาปัจจุบันไปที่ `bookings.quoted_price`
- การแก้ราคาในโปรไฟล์มีผลเฉพาะการจองใหม่
- การจองเดิม การส่งสลิป คิวแอดมิน แชต และรายงานอ่านราคาจาก `bookings.quoted_price`
- สมาชิกส่งยอดตามราคาที่บันทึกไว้ ระบบยังคงให้แอดมินตรวจหลักฐานด้วยตนเอง

## 7. Workflow การจองและชำระเงิน

### 7.1 สร้างการจอง

`POST /v1/bookings` รับ `trainerId`, `slotId` และ `note` ตาม contract ปัจจุบัน

ใน transaction เดียว API ต้อง:

1. ตรวจและล็อก slot ด้วย `FOR UPDATE`
2. ตรวจว่าเทรนเนอร์ได้รับอนุมัติ ผู้ใช้ยัง active slot ยังว่าง และราคาใช้ได้
3. สร้าง booking สถานะ `awaiting_payment`
4. คัดลอกราคาต่อครั้งไป `quoted_price`
5. ตั้ง `payment_deadline_at = UTC_TIMESTAMP() + 10 นาที`
6. เปลี่ยน slot เป็น `held`
7. บันทึก history ว่าสมาชิกสร้างการจองและเริ่มรอชำระ
8. สร้างห้องแชตตามพฤติกรรมเดิม

response ส่ง `id`, `status`, `quotedPrice` และ `paymentDeadlineAt` เพื่อให้ UI ใช้เวลาจากเซิร์ฟเวอร์

### 7.2 อัปโหลดสลิปครั้งแรก

- สมาชิกอัปโหลดได้เมื่อ booking เป็น `awaiting_payment` และเวลาปัจจุบันน้อยกว่า `payment_deadline_at` เท่านั้น เมื่อเวลาเท่ากับเส้นตายถือว่าหมดเวลา
- API ล็อก booking และตรวจเส้นตายซ้ำก่อนบันทึกไฟล์
- หากทันเวลา booking เปลี่ยนเป็น `payment_review` และ slot ยังเป็น `held`
- การรอแอดมินตรวจไม่มีตัวนับ 10 นาที
- หากเลยเวลา API เปลี่ยน booking เป็น `expired`, คืน slot และลบไฟล์ที่รับไว้ก่อน transaction ล้มเหลว

### 7.3 การตรวจโดยแอดมิน

- อนุมัติ: payment เป็น `approved`, booking เป็น `confirmed`, slot เป็น `booked`
- ปฏิเสธครั้งแรก: payment เป็น `rejected`, booking กลับเป็น `awaiting_payment`, ตั้ง `payment_deadline_at` ใหม่อีก 10 นาที และ slot ยังเป็น `held`
- สมาชิกอัปโหลดสลิปใหม่ได้หนึ่งครั้งโดยใช้ payment record ใหม่
- ปฏิเสธครั้งที่สอง: payment เป็น `rejected`, booking เป็น `expired`, slot เป็น `available`
- หากสมาชิกไม่ส่งครั้งที่สองทันเวลา ผลลัพธ์เป็น `expired` เช่นเดียวกัน

จำนวนครั้งใช้ payment records เดิมของ booking ไม่เพิ่มคอลัมน์ attempt counter หาก booking มี payment ที่ถูกปฏิเสธแล้วหนึ่งรายการ การปฏิเสธ payment รายการถัดไปถือเป็นครั้งที่สองและทำให้ booking หมดอายุ

## 8. การหมดเวลาแบบตรวจเมื่อมีการใช้งาน

ระบบไม่เพิ่ม cron, worker หรือ MariaDB Event Scheduler

สร้างกลไก expiry กลางใน backend แล้วเรียกก่อนอ่านหรือเปลี่ยนข้อมูลที่เกี่ยวข้อง ได้แก่:

- รายการและรายละเอียดเทรนเนอร์
- รายการ slot
- การสร้าง booking
- รายการ booking ของแต่ละบทบาท
- การอัปโหลดสลิป
- คิวตรวจของแอดมินเมื่อเกี่ยวข้อง

กลไกเลือก booking ที่ `status = awaiting_payment` และ `payment_deadline_at <= UTC_TIMESTAMP()` แล้วเปลี่ยนเป็น `expired`, คืน slot เป็น `available` และบันทึก history ภายใน transaction

`bookings` ต้องมี index ที่รองรับ `status` และ `payment_deadline_at` การสร้าง booking ใหม่ยังล็อก slot ด้วย `FOR UPDATE` จึงไม่มีสอง booking ที่ถือ slot เดียวกัน แม้คำขอ expiry และคำขอจองใหม่มาถึงพร้อมกัน

บนหน้า member ตัวนับใช้ `paymentDeadlineAt` จาก API และเวลาปัจจุบันเพื่อแสดงผลเท่านั้น เมื่อถึงศูนย์ UI เรียกโหลดสถานะใหม่ การตัดสินจริงยังอยู่ที่ PHP และเวลาของฐานข้อมูล

## 9. สถานะและฐานข้อมูล

### 9.1 Booking

เพิ่ม:

- `status = expired`
- `payment_deadline_at DATETIME NULL`
- index `(status, payment_deadline_at)`

สถานะ `pending_trainer` ไม่ใช้กับการจองใหม่และถูกนำออกจาก enum หลัง migration รายการเดิมที่ยังเป็น `pending_trainer` เปลี่ยนเป็น `expired`, คืน slot เป็น `available` และเพิ่ม history ว่า workflow เปลี่ยนและสมาชิกต้องจองใหม่

รายการเดิมที่เป็น `awaiting_payment` และยังไม่มี `payment_deadline_at` ได้เส้นตายใหม่ 10 นาทีจากเวลาที่ migration ทำงาน เพื่อให้สมาชิกมีโอกาสส่งหลักฐานหนึ่งช่วงเวลา รายการ `payment_review`, `confirmed`, `completed`, `cancelled` และประวัติเดิมไม่เปลี่ยนสถานะ

### 9.2 Slot

- `available`: พร้อมให้จอง
- `held`: การจองกำลังรอสมาชิกส่งสลิปหรือรอแอดมินตรวจ
- `booked`: แอดมินอนุมัติการชำระเงินแล้ว
- `blocked`: เทรนเนอร์ปิดช่วงเวลา

### 9.3 History

บันทึกทุก transition รวมถึง:

- สร้าง booking และเริ่ม 10 นาที
- อัปโหลดสลิป
- แอดมินอนุมัติหรือปฏิเสธ
- เริ่มเวลาแก้ไข 10 นาที
- หมดเวลา
- ปฏิเสธครั้งที่สอง

ใช้ข้อความไทยที่บอกสาเหตุจริงและไม่กล่าวว่าเป็นการตรวจอัตโนมัติ

## 10. การเปลี่ยนพื้นที่เทรนเนอร์

- ลบคิว “คำขอรอตอบรับ” ปุ่มรับ ปุ่มปฏิเสธ และช่องกรอกราคา
- slot ที่ booking เป็น `awaiting_payment` หรือ `payment_review` แสดงเป็น “ล็อกชั่วคราว” แบบอ่านอย่างเดียว
- booking ที่ `confirmed` แสดงเป็นนัดที่ยืนยันแล้วตามเดิม
- เทรนเนอร์ยังปิดงานหลังเวลานัดสิ้นสุดตามกฎเดิม
- การหมดอายุไม่สร้างงานที่เทรนเนอร์ต้องจัดการ

## 11. สถานะหน้าจอและข้อความ

ข้อความหลัก:

- `awaiting_payment`: “อัปโหลดสลิปภายใน 10 นาที”
- `payment_review`: “ส่งหลักฐานแล้ว รอผู้ดูแลตรวจ”
- `confirmed`: “ยืนยันการจองแล้ว”
- `expired`: “การจองหมดเวลา ช่วงเวลานี้ถูกคืนแล้ว”
- การแก้ไขครั้งแรก: “สลิปไม่ผ่าน กรุณาส่งใหม่ภายใน 10 นาที”
- ปฏิเสธครั้งที่สอง: “สลิปครั้งที่สองไม่ผ่าน การจองถูกยกเลิกแล้ว”

ทุกหน้าที่เกี่ยวข้องต้องมี loading, empty, error, retry, disabled, busy และ success state ที่ไม่สร้างสถานะปลอม

ข้อผิดพลาดสำคัญ:

- slot ถูกจองไปแล้ว: แจ้งให้เลือกเวลาใหม่และโหลดตารางล่าสุด
- เส้นตายผ่านระหว่างอัปโหลด: แจ้งว่าการจองหมดเวลาและไม่เก็บไฟล์กำพร้า
- API โหลดสถานะไม่ได้: หยุดตัวนับในสถานะไม่แน่นอน แสดง retry และไม่เดาว่า slot ถูกคืนแล้ว
- การส่ง booking ซ้ำ: ปิดปุ่มระหว่างทำงานและให้ transaction เป็นตัวตัดสินสุดท้าย

## 12. Accessibility และ responsive

- เป้าหมาย WCAG 2.2 AA ตาม `DESIGN.md`
- label เชื่อมกับ field และห้ามใช้ placeholder แทน label
- focus ring 3px มองเห็นได้บนพื้นสว่างและพื้นเข้ม
- สถานะทุกชนิดใช้ข้อความหรือไอคอนร่วมกับสี
- `Sheet`, `Dialog` และ disclosure ปิดได้ด้วยคีย์บอร์ด มีชื่อ accessible และคืน focus ถูกตำแหน่ง
- ตัวนับเวลาใช้ `role=status` แบบไม่ประกาศทุกวินาที ประกาศเฉพาะจุดสำคัญและเมื่อหมดเวลา
- reduced motion ปิดการเลื่อนและ transition ที่ไม่จำเป็น
- ตรวจ 320, 375, 414, 768 และ 1280px รวมถึง 200% zoom

## 13. การทดสอบ

### 13.1 Frontend

- ตัวกรอง คำค้น การเรียงลำดับ empty state และ card facts
- `Sheet` มือถือและลำดับ focus
- โปรไฟล์ ราคา slot selection และ Dialog ยืนยัน
- request สร้าง booking ไม่มีราคาใน body และใช้ราคา response จาก API
- ตัวนับก่อนครบ ตรงเส้นตาย และหลังเส้นตายด้วย fake timer
- สถานะอัปโหลดครั้งแรก การแก้ไขครั้งเดียว ยืนยัน และหมดอายุ
- พื้นที่เทรนเนอร์ไม่มีปุ่มรับ ปฏิเสธ หรือกรอกราคา
- สถานะ `expired` แสดงเหตุผลและทางกลับไปเลือกเวลา

### 13.2 PHP และฐานข้อมูล

- การคัดลอกราคาจากโปรไฟล์ไป booking
- ไม่อนุญาต trainer ที่ไม่มีราคาที่ใช้ได้
- expiry ก่อนเส้นตาย ตรงเส้นตาย และหลังเส้นตาย
- สองสมาชิกพยายามจอง slot เดียวกันพร้อมกัน
- อัปโหลดสลิปแข่งกับ expiry
- ปฏิเสธครั้งแรกตั้งเส้นตายใหม่
- ปฏิเสธครั้งที่สองคืน slot
- การเรียก expiry ซ้ำไม่สร้าง history ซ้ำและไม่เปลี่ยน slot ผิดสถานะ
- migration และ schema ติดตั้งใหม่ได้

### 13.3 ขั้นตอนครบวงจร

ทดสอบเทรนเนอร์ที่อนุมัติแล้วตั้งราคาต่อครั้งและสร้าง slot จากนั้นสมาชิกค้นหา เปิดโปรไฟล์ เลือกเวลา จอง อัปโหลดสลิปภายใน 10 นาที แอดมินปฏิเสธ สมาชิกส่งใหม่ และแอดมินอนุมัติ แล้วทดสอบแชต ปิดงาน และรีวิวตาม workflow เดิม

ทดสอบอีกเส้นทางโดยไม่อัปโหลดสลิปจนหมดเวลา แล้วให้สมาชิกอีกคนจอง slot เดิม ตรวจ booking, booking history, payments, chat room และ availability slot ใน phpMyAdmin

รัน frontend tests, PHP tests, lint, typecheck, production build, live XAMPP smoke และ database audit

## 14. Migration และการส่งมอบ

- สำรองฐานข้อมูล XAMPP ก่อน migration
- migration ต้องรันซ้ำได้อย่างปลอดภัยหรือหยุดพร้อมข้อความที่ชัดเจน
- ตรวจจำนวน `pending_trainer` เดิม เปลี่ยนเป็น `expired`, คืน slot และบันทึก history ก่อนนำค่าออกจาก enum
- กำหนดเส้นตาย 10 นาทีจากเวลา migration ให้ `awaiting_payment` เดิมที่ยังไม่มี deadline
- อัปเดต `schema.sql`, seed, audit SQL, smoke script, API types และเอกสาร workflow ให้ตรงกัน
- ห้ามลบ payment, booking history, chat หรือ review เดิม
- เก็บหลักฐาน booking ID, จำนวนแถวที่เกี่ยวข้อง และผลตรวจ slot หลังแต่ละเส้นทาง

## 15. เกณฑ์ยอมรับงาน

- หน้าค้นหาและหน้าโปรไฟล์ตรงกับโครง Marketplace Grid และ Commerce Detail ที่อนุมัติ
- UI ยังคงระบบภาพ FitConnect และใช้ shadcn โดยไม่เพิ่มไลบรารี UI ชุดใหม่
- ราคาที่สมาชิกเห็นตอนจองตรงกับ `bookings.quoted_price`
- การจองใหม่ไม่ผ่าน `pending_trainer` และไม่มีคำสั่งรับหรือปฏิเสธสำหรับเทรนเนอร์
- สมาชิกมีเวลาอัปโหลดสลิป 10 นาทีจากเวลาของเซิร์ฟเวอร์
- การปฏิเสธครั้งแรกให้เวลาใหม่ 10 นาทีเพียงครั้งเดียว
- การหมดเวลาหรือปฏิเสธครั้งที่สองคืน slot ให้สมาชิกอื่นจองได้
- ไม่มีการจองสองรายการถือ slot เดียวกัน
- แอดมินยังเป็นผู้ตรวจสลิปและข้อความไม่กล่าวว่าเป็นการตรวจอัตโนมัติ
- ข้อมูลทุก transition ตรวจได้ใน phpMyAdmin
- หน้า 320 ถึง 1280px, keyboard, 200% zoom และ reduced motion ผ่านข้อกำหนด
- frontend, PHP, lint, typecheck, build, smoke และ database audit ผ่านก่อนส่งมอบ
